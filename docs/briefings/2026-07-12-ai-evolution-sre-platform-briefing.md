# 智能运维 AI 演进资料（领导汇报扩展版）

> **描述：** 供同事编写企业智能运维 / SRE 路线及 AI 场景建设材料时引用；可拆成 15～20 页 PPT，或作为路线附录原文。材料明确「智能运维 / SRE 平台」与「数字员工控制平面」叠加关系，并给出近约三个月可启动的第一步。
> **口径：** 概念与阶段为主，不使用产品内部代号；统一称「数字员工控制平面」。
> **日期：** 2026-07-12（扩展版）

---
## 1. 背景与主张

智能运维要引进 AI，成败不在「先上多大模型」，而在「先有没有可调用的数据标准、干净事实、以及可治理的场景边界」。

**主张：** 先底座，再场景，再接入中台，再规模化治理。底座不牢，场景只会演示好看、生产不可控。

**演进主线：**

> 标准清洗 → 场景编排 → 平台调用 → 规模治理
> 先让数据说人话，再让场景可复用，再让平台可一键调用，最后用制度把智能管住。

**与现有建设的关系：**

- 企业侧正在建设的 **智能运维 / SRE 平台**：继续作为运维事实入口（资产、告警、工单、观测、变更窗口等）。
- 本项目提供的 **数字员工控制平面**：作为可引入的 **AI 场景能力中台**，负责场景编排、数字员工执行、人机审批、证据回写与审计留痕。
- 两者是 **叠加关系，不是替代关系**：运维平台管「运维业务闭环」，数字员工控制平面管「AI 如何被安全地调用与治理」。

## 2. 为什么先打基础

在正式堆 AI 场景之前，建议先把下列基础做实。否则模型再强，也只能停留在演示层；即便接入数字员工控制平面，也会因为输入不可信而无法形成可汇报、可复盘的成果。

### 2.1 数据化与标准接口

- 资产、服务、告警、工单、变更等核心对象有统一标识与字段约定
- 对外提供稳定、可版本化的标准接口（可被场景按契约消费）
- 明确「谁拥有主数据、谁可写回结论」，避免多系统各说各话
- **对接数字员工控制平面时的含义：** 场景输入应尽量来自标准接口或已清洗的事实切片，而不是临时粘贴日志；结论通过结构化对象回写，而不是聊天记录

### 2.2 降维清洗与语义对齐

- 日志、指标、告警做降噪与聚合，把刷屏信息收敛为业务可理解视图
- 统一术语与字典（同一服务、同一影响面、同一严重级别含义一致）
- 过滤无效噪声，保留可推理、可复盘的关键事实
- **对接数字员工控制平面时的含义：** 数字员工执行时只注入「当前任务需要的上下文切片」，而不是全量原始数据；清洗质量直接决定场景质量

### 2.3 可观测事实与可审计动作

- 场景输入来自可核验的事实，而非口头描述或临时截图
- 场景输出（建议、结论、证据）可回写、可追溯
- 任何自动或半自动动作留审计记录，满足国企治理与汇报要求
- **对接数字员工控制平面时的含义：** 平台原生支持审批、审计、工件与决策记录；运维侧需保证上游事实可对账，下游动作可追责

### 2.4 不做基础时的典型后果

- 场景「看起来聪明」，但结论无法复核、无法进工单
- 同一告警多套说法，根因建议互相打架
- 一旦尝试自动处置，风险边界不清，无法对领导负责
- 接入中台后仍反复「人工救火」，无法形成可复制的场景资产

## 3. 数字员工控制平面是什么：可作为 AI 场景能力中台

### 3.1 一句话定位

**数字员工控制平面**：把 AI 执行能力、流程调度、人类审批、上下文、工件和审计纳入统一控制平面，让智能场景可编排、可调用、可治理。

它不是又一个监控系统，也不替代 SRE 平台的资产 / 告警 / 工单主链路；它解决的是：

> 「运维系统触发一个 AI 场景之后，谁来执行、如何确认、证据写到哪、全过程如何审计。」

### 3.2 分层架构（领导可讲清的四层）

| 层 | 职责 | 不做什么 |
|----|------|----------|
| **Console（控制台）** | 管理、观察、审批、验收入口 | 不当本机执行器，不当长期业务事实源 |
| **Control Plane（控制平面）** | 业务状态、任务、审批、审计、流程调度、上下文、工件；对运维平台与执行侧提供 API | 不直接在业务机上跑命令 |
| **Runtime Agent（运行时）** | 领任务、维护租约、管理本机 Provider 进程 / 会话、工作目录、日志、工件、执行槽位 | 不承载业务策略与长期业务状态 |
| **Provider（执行引擎）** | 在 Runtime 管理下实际执行 AI 能力（如各类 Code / Agent 运行时） | 不承载平台级状态 |

另有两类关键能力层：

- **Capability（外部能力）**：外部系统 / MCP 等能力的注册、绑定、凭据、授权与调用审计——适合把运维平台、CMDB、知识库、工单系统接成「可被场景调用的能力」。
- **Authorization（授权）**：关系型授权与决策记录，保证「谁能对什么对象做什么」可判定、可追溯。

### 3.3 核心业务对象（写进路线时建议统一用这套语言）

| 对象 | 含义 | 对运维 AI 场景的价值 |
|------|------|----------------------|
| **数字员工** | Agent 型业务身份：角色、任务边界、权限、上下文策略、输出契约 | 把「某个 AI 场景由谁执行」固化成可管理身份，而不是散落脚本 |
| **人类** | 一等的管理、审批、决策、验收参与者 | 高风险动作必须人类拍板，AI 不能绕过 |
| **Project（项目 / 业务闭环容器）** | 面向具体目标或问题场景的闭环：目标、负责人、协调线程、任务、证据、预算、审批、验收 | 一次重大故障处置、一次变更窗口评估、一条业务线试点，都可落成 Project |
| **虚拟协调线程** | 项目内置协调状态机（串行决策、并发分派执行） | 保证「先决策、再分派、再回收证据」，避免多 Agent 自由聊天失控 |
| **任务 / 路由决策** | 结构化派工与决策记录 | 每次 AI 参与都留下「为什么派、派给谁、结果是什么」 |
| **审批 / 收件箱** | 人类决策入口 | 领导关心的「人要确认」有正式承载 |
| **工件与证据** | 可持久化的产出物 | 汇报、复盘、审计有材料，而不是聊天记录 |
| **上下文策略** | 全局上下文持久化，执行时只注入任务所需切片 | 控制成本与泄密面，提升场景稳定性 |

### 3.4 协作原则（与国企治理天然对齐）

1. **人类是一等公民**：负责人、审批人、验收人固定可绑；最终业务判断不交给模型。
2. **Agent 不自由聊天**：通过结构化对象协作，每个阶段必须产出可持久化的工件、证据、决策或交接包。
3. **高风险必须暂停**：需求歧义、权限不足、变更发布、删除写入、测试失败后的业务判断等，进入人类确认。
4. **客户差异配置化**：不靠改核心流程硬编码，而靠能力注册、策略与语义映射吸收差异——便于后续多条线复制。

### 3.5 与智能运维 / SRE 平台的职责切分

| 能力域 | 建议归属 | 说明 |
|--------|----------|------|
| 资产 / CMDB、监控指标、告警收敛、工单流转、变更窗口 | **运维 / SRE 平台** | 继续做运维事实源与一线入口 |
| 场景剧本、数字员工、任务编排、人机审批、证据与审计 | **数字员工控制平面** | 做 AI 场景控制与治理 |
| 日志/指标原始采集与长期存储 | **现有观测体系** | 数字员工控制平面消费切片，不替代观测底座 |
| 知识库 / Runbook / 历史工单语义 | **双方协同** | 运维侧沉淀内容；经 Capability / 标准接口供场景调用 |
| 自动处置、自动变更 | **默认不启用** | 需完成分级、审批与红线后，才允许半自动或有限自动 |

**一句话：** 运维平台负责「看见问题、管住流程」；数字员工控制平面负责「把 AI 场景变成可调用、可确认、可复盘的能力」。

## 4. 运维侧 AI 场景清单（宽泛点名）

汇报时可先点名下列场景，细节按阶段故事与平台能力展开：

1. **告警降噪** — 同类告警聚合，突出业务影响
2. **根因辅助** — 关联变更与历史模式，给出排查方向
3. **变更风险评估** — 窗口前识别冲突与风险等级
4. **知识问答** — 基于 runbook / 历史工单的值班问答
5. **处置建议** — 给出建议步骤，默认不自动执行

原则：前期以「建议级、辅助决策」为主；未完成分级与审批前，不上自动变更 / 自动处置。

### 4.1 场景与数字员工控制平面能力的粗映射

| 场景 | 主要用到的平台能力 | 建议风险级别（起步） |
|------|--------------------|----------------------|
| 告警降噪 | 上下文切片、任务执行、工件回写 | 只读建议 |
| 根因辅助 | 数字员工 + 外部能力调用（变更/工单/知识）+ 证据 | 只读建议 + 值班确认 |
| 变更风险评估 | Project 闭环 + 审批 + 审计 | 建议 + 负责人确认 |
| 知识问答 | Capability 接知识源 + 输出契约 | 只读 |
| 处置建议 | 场景编排 + 强制人机确认 | 建议；执行仍走人工/现有变更流程 |

## 5. 四阶段演进（融入平台建设节奏）

### 阶段一：标准与清洗

| 项 | 内容 |
|----|------|
| **目标** | 让 AI「看得见、说得准」——同一对象、同一指标、同一事件有统一语义 |
| **运维侧基础工作** | 资产 / 服务 / 告警 / 工单主数据与接口标准；日志指标降维与噪声清洗；关键字段字典与权限边界 |
| **数字员工控制平面侧可并行准备** | 控制台与控制平面可用；数字员工与团队治理就绪；Capability 预留对接运维 API / 知识源的注册位；契约与鉴权打通 |
| **故事示例** | 同类告警从「几十条刷屏」收敛为「一条业务影响视图」，人先看懂，再谈智能 |
| **阶段出口** | 核心对象可 API 拉取；样例数据可被场景稳定消费；有最小数据质量看板；中台侧具备「接得住输入、写得回输出」的最小通路 |

**阶段一不追求：** 大规模自动处置、跨多条线复制、无人值守闭环。

### 阶段二：场景编排

| 项 | 内容 |
|----|------|
| **目标** | 把零散能力编成可复用的「场景剧本」 |
| **运维侧基础工作** | 选 1～2 个低风险辅助场景试点；定义输入 / 输出契约；明确哪些动作只能建议、不能自动执行 |
| **数字员工控制平面侧落地** | 为试点场景创建 Project 或等价业务闭环；配置数字员工（角色、边界、输出契约）；用协调线程串行决策、分派任务；产出结构化 RouteDecision / Task / 工件；人类确认点进审批 / 收件箱 |
| **故事示例** | 夜间告警触发「根因辅助」：汇总关联变更与近期故障模式，给出 Top3 可能原因与排查清单，由值班人在收件箱确认 |
| **阶段出口** | 至少 1 个建议级场景端到端跑通；有场景目录与成功 / 失败判定口径；每次运行有证据与审计，而不是聊天截图 |

**阶段二强调：** 「剧本化」比「模型炫技」更重要；输出必须结构化，才能进入阶段三被平台稳定调用。

### 阶段三：平台接入调用

| 项 | 内容 |
|----|------|
| **目标** | 场景由中台统一承载，被运维平台稳定调用，而不散落在个人脚本里 |
| **运维侧基础工作** | 在告警详情 / 工单 / 变更窗口等入口增加「触发 AI 场景」；接收结论与证据回写；失败时降级人工 |
| **数字员工控制平面侧落地** | 对外 API / Capability 调用约定固定；运维平台触发 → Control Plane 开任务 / 入 Project → Runtime 执行 → 结论与工件回写 → 高风险进人类审批；全链路审计可查 |
| **故事示例** | 变更窗口前一键调用「变更风险评估」：返回风险等级、冲突变更、回滚建议；高风险须负责人确认后才进入窗口 |
| **阶段出口** | 2～3 个场景可从现网入口稳定调用；调用链路有审计；失败可降级为人工流程；领导可在控制台看到「谁触发、谁确认、结论是什么」 |

**推荐调用链路（示意）：**

```text
运维/SRE 平台（告警/工单/变更入口）
    → 标准接口触发场景
    → 数字员工控制平面 Control Plane（编排 / 任务 / 审批）
    → Runtime + Provider（执行）
    → 结构化结论 + 工件 + 审计
    → 回写运维平台（工单备注 / 事件字段 / 附件证据）
```

### 阶段四：规模化与治理

| 项 | 内容 |
|----|------|
| **目标** | 从试点到可运营：场景可复制、效果可度量、风险可控 |
| **运维侧基础工作** | 场景分级上线制度；效果指标（降噪率、辅助采纳率、误报率）；条线复制与培训 |
| **数字员工控制平面侧落地** | 场景目录与数字员工目录可运营；权限与 Runtime 范围策略收紧；预算 / 配额纳入 Project；定期复盘升级或冻结场景；禁止无审批的自动处置扩散 |
| **故事示例** | 「知识问答」覆盖多条线 runbook；「处置建议」仍保持建议 + 确认；用复盘数据决定哪些场景升级、哪些冻结 |
| **阶段出口** | 场景目录可运营；有治理制度与度量；领导层能看到投入产出与风险边界；AI 成为可管理的组织能力，而不是个人工具 |

## 6. 接入形态：运维平台如何「调用」数字员工控制平面

以下写得偏宽泛，便于路线材料引用；实施时再落具体接口名与联调清单。

### 6.1 三种常见接入深度

| 深度 | 形态 | 适用阶段 | 说明 |
|------|------|----------|------|
| **L1 旁路辅助** | 运维人员在控制台手工发起场景，结论人工贴回工单 | 阶段二 | 最快验证价值，改造成本低 |
| **L2 入口触发** | 告警 / 工单 / 变更页一键触发，结论自动回写 | 阶段三 | 推荐作为「平台接入调用」的主形态 |
| **L3 事件驱动** | 告警升级、变更提交等事件自动开场景；高风险仍强制审批 | 阶段四（有选择） | 必须先有分级、降级与审计，否则治理风险高 |

### 6.2 建议的最小契约（领导听「有标准」即可）

每次场景调用至少约定：

1. **输入**：场景类型、关联对象 ID（告警 / 工单 / 服务）、事实切片引用、发起人
2. **控制**：是否允许自动执行、必须人工确认的门槛、超时与降级策略
3. **输出**：结构化结论、建议列表、证据 / 工件引用、风险等级、确认状态
4. **审计**：触发时间、执行身份（数字员工）、确认人、最终状态

### 6.3 人类确认如何落在平台上

- 建议级场景：值班人确认「采纳 / 不采纳 / 需补充」
- 变更与高风险：项目人类负责人或指定审批人确认
- 确认入口：数字员工控制平面审批 / 收件箱；也可在运维平台嵌入状态，但 **决策事实以控制平面为准**

### 6.4 不建议一上来就做的事

- 让模型直接改生产配置、直接执行变更而不经审批
- 用「自由多 Agent 聊天」替代结构化任务与证据
- 把运维主数据迁进 AI 中台，造成双主数据
- 未完成数据清洗就做全量事件驱动自动开场景

## 7. 领导一句话路线图与价值表述

**路线图金句：**

> 标准清洗 → 场景编排 → 平台调用 → 规模治理。
> 先让数据说人话，再让场景可复用，再让平台可一键调用，最后用制度把智能管住。

**平台价值金句（可配一页）：**

> 用数字员工控制平面，把 AI 从「个人工具」升级为「可编排、可审批、可审计的组织能力」；
> 与智能运维平台叠加，而不是推倒重来。

**对领导可承诺的治理点：**

- 高风险动作有人确认
- 每次 AI 参与有证据与审计
- 场景可分级、可冻结、可复盘
- 失败可降级回人工，不影响现网主流程

## 8. 近三个月可做的第一步

建议将下列动作纳入约三个月时间盒，写进汇报结尾：

1. **选定 1 条业务线**，完成告警 / 资产 / 工单三类对象的最小标准接口与样例数据。
2. **只试点 1 个建议级场景**（优先告警降噪或根因辅助），明确输出契约与人工确认点。
3. **在数字员工控制平面侧建最小闭环**：试点 Project、数字员工、任务产出与审批入口跑通。
4. **约定调用方式**：运维平台触发（先 L1 手工，再 L2 一键）→ 中台跑场景 → 结论回写工单 / 事件 → 全链路可查。
5. **同步定一条红线**：未完成分级与审批前，不做自动变更 / 自动处置上线。

## 9. 风险、边界与常见误区

| 误区 | 建议口径 |
|------|----------|
| 「先上大模型再补数据」 | 先标准与清洗，模型是执行手段不是前提 |
| 「AI 替代值班与审批」 | AI 辅助，人类仍是决策与验收主体 |
| 「接入中台就要替换运维平台」 | 叠加能力，运维事实入口仍在 SRE 平台 |
| 「场景越多越好」 | 先 1～2 个建议级跑通，再复制 |
| 「能自动就尽量自动」 | 自动是治理结果，不是起步目标 |
| 「聊天记录就是证据」 | 必须结构化工件、任务结论与审计记录 |

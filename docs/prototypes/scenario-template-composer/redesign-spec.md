# 场景模板创建/编辑页重构方案

状态：评审中。原型对照：`soft-b-master-detail.html`（骨架）+ `soft-a-chain-inspector.html`（顶部概览条）。本稿约束 UI 结构、交互与前端映射；服务端 SpecV2 / 版本表语义不改。

## 0. 已拍板

1. 「复制现有模板」只列 **active** 模板。
2. **产品面去掉「升版」**。作者动作是「保存更改」。后台仍走不可变版本行（见 §8），不给人看「发新版」心智。
3. 模板页 **不** 掺项目编制就绪度。
4. 词表已停用席位：编辑页仍显示并标「已停用」，保存前必须换成 active。
5. **一期只做串行骨架。** 并行（如种子 `software_delivery` 的审查 ∥ 测试）不进本期编辑器；现有并行 spec 禁止被本页保存改写（§7.1）。
6. **收口文案**：默认用站名；检修台可选填「收口怎么叫」，写入 `exits[].label`（确认卡 / 就绪度读这一列）。

## 1. 结论

以主从编排台为骨架、关卡链压缩为顶部只读概览条，全页 `/scenario-templates/new` 与 `/scenario-templates/$key/edit` 取代新建/升版弹窗。

模板只回答：这类活必须经过哪些**席位**、谁验、哪几站可以当**收口**。席位来自角色词表；人在项目编制里绑；这次跑多深由规划确认卡选交付出口，**不是**任务发起时选。

## 2. 三条对象怎么咬合（方案原先写偏的地方）

```
角色词表          场景模板                 项目编制              任务发起 / 规划
席位登记          引用席位、声明收口         席位→具体员工         只选模板，不选深度
role_key          skeleton[].role          casting.role_key      scenario_template_key
active 才能写入    roles[].key 必须在词表    按 template_key 绑    只列 active 模板
停用有引用冲击     保存后主表 spec 即当前     缺员 → 就绪度缺口     展示编制 + 可跑到哪档
```

### 2.1 和角色词表

- 检修台「谁来接收 / 独立验证角色」**只**能选自 `status=active` 的词表。禁止手填新 key。词表空 → 引导去 `/role-vocabulary` 先登记，与现弹窗一致。
- 保存时服务端 `validateSpecRoles`：`roles[].key` 与 `skeleton[].role` 必须是租户 **active** 词表键，否则 400 `unknown role keys`。停用中的席位不能再写进新保存的 spec。
- 同一席位可以出现在多站（故障处置里「诊断」接定界又接根因）——编制仍是「这个模板的这个 role_key 绑谁」，不是按站绑人。
- 词表停用会查 references（哪些模板 spec 还引用该 key、多少员工持有、多少编制行）。**不停用不会改已保存模板**；已跑计划钉住旧 spec。下次有人点「保存更改」才会被拒。
- 员工 `role_keys`、项目编制、规划缺口补员都认词表 key。模板里写了一个项目从未编制的席位 → 发起页就绪度变为「暂不可跑 · 缺 …」，这是预期，不是模板页要解决的。

### 2.2 和任务发起（当前真实行为）

任务发起（`task-launch-form.tsx`）**不选深度、不选站**：

1. 选项目、选 **active** 场景模板（卡片：名称 + 描述）。
2. 旁路展示该项目对该模板的**编制**，以及 `playbook-readiness`：`可跑 · {deepest_exit.label}` 或 `暂不可跑 · 缺 {roles}`。
3. POST 需求只带 `scenario_template_key`。
4. **深度发生在规划**：planner 按需求从 `spec.exits` 里选**最浅**满足的 `exit_deliverable`；确认卡（收件箱）可「改选交付出口」，选项 = 当时钉住的 `available_exits`。
5. 服务端按该出口 `PruneSkeletonForExit` 剪枝骨架再派发。

因此创建页的「出口表」不是模拟发起人点哪一站，而是预告：

| 作者在模板里标的 | 下游谁消费 |
|---|---|
| 模板名称 / 描述 | 发起页模板卡片 |
| 各站角色 | 项目编制要填的席位；就绪度 `required_roles` / `missing_roles` |
| 「可作出口」+ 出口文案（默认用站名） | 确认卡「交付出口」；就绪度 `deepest_exit.label`；planner 的 exits 集合 |
| 必须经过 / 人类门 / 独立验证 | 剪枝后仍命中的约束（`when.exit_at_or_beyond`） |

发起页**看不到**关卡链本身。作者若只把结构写对、名称/描述/出口文案含糊，发起人会选错模板。身份区文案与出口标签是给发起/确认用的，不是内部备注。

### 2.3 方案原先的走偏

- 把出口写成「发起时选深度」→ 与现状不符。应改称 **收口档位预览**。
- 把「升版」当产品动作 → 作者要的是改这份配置；版本表的意义是**进行中计划钉住 spec**，不是给人翻历史。

## 3. 目标 / 非目标

**目标**

- 一般用户：加站 → 从词表分派席位 → 标哪些站可收口 → 保存。
- 链与单站同屏；收口表随 draft 即时更新。
- Soft-Flat + 主从详情；复用既有组件。

**非目标**

- 不做 BPMN / 并行网关。并行骨架的定义与编辑留到下一阶段；本期既不提供菱形图画，也不默默把旧并行图拉直。
- 不在模板绑人；不在模板页拉某个项目的就绪度。
- 不改 SpecV2 契约；不删 `scenario_template_versions`。
- JSON 对照只读，避免和第二套编辑源打架。

## 4. 路由与文案

| 动作 | 现状 | 目标 |
|---|---|---|
| 新建 | 弹窗 | `/scenario-templates/new`，主按钮「保存」 |
| 更改配置 | 行内「升版」弹窗 | `/scenario-templates/$key/edit`，主按钮「保存更改」；列表按钮改为「编辑」 |
| 启停 | 列表 | 不动 |
| 复制起步 | 无 | 仅新建页：下拉 active 模板，灌入 draft，名称/标识留空重填 |

取消回列表。编辑页内部标识只读；名称/描述随保存一起更新（spec 走 `POST .../versions`，元数据走既有 `PATCH`，一次点击串起来，失败要可重试、不假装成功）。

## 5. 页面布局

与前稿相同：身份区 → 关卡链概览（只读，点站=选中）→ 左队列 + 右检修台（`MasterDetailLayout` rail 340）→ **收口档位预览**（原「发起预览」改名）。

检修台在「可作出口」勾选后出现选填「收口怎么叫」；空白则预览和保存都用站名。

收口表列：档位（浅→深）/ 停在哪一站 / 走到这里要经过哪些席位 / 人类门。表尾说明改为：

> 任务发起只选这份模板。规划时会从这些收口里选一档（默认尽量浅）；确认卡可以改选。本表不反映某个项目缺不缺人。

保存文案不要「保存为第 N 版」。

## 6. 组件与词表加载

同前稿组件表。角色选择只渲染 active 词表；`isPending` 显示「加载角色词表…」，禁止闪「还没有启用中的剧本角色」。

队列徽标：出口 = brand-soft；人类门 = warn-soft。一行最多这两枚。

## 7. `spec-composer.ts`

节点增加 `exit: boolean`。**出口集合以勾选为准**，废弃「原 exits 的 produce 仍在就整表保留」——否则取消勾选会被旧 spec 吞掉。

`when.exit_at_or_beyond` / `applies_from_exit`：取该站及之后最近的已声明出口。站落在所有出口之后 → 校验阻断。

编辑/复制必须把**打开时的完整 spec** 当作 `original` 传入 `specFromComposer`，以保留 `required_capabilities`、`produces_defaults`、`required_inputs_defaults`、`collapse_rules`、`autonomy_*` 等本页不编辑的字段。新建空白模板这些为空，可接受（编制按 role_key，能力提示为空）。

`exits[].label`：该站勾了出口时，用「收口怎么叫」trim 后的值，空则用站名（再空则用角色名）。

### 7.1 串行一期 vs 并行以后

**为什么现在只做串行：** 一般用户要配的是「谁接、谁验、哪能停」。并行要表达的是依赖图（多前置、同层可同时开），编辑器和校验、剪枝、确认卡文案都会明显变重。一期用队列就能覆盖故障处置、运维分析、以及用户自己加的任意串行站数；这是 MVP 和工作量的合理切分。SpecV2 本身已能表达并行，种子 `software_delivery` 继续按原 spec 规划，不需要本期去「升级」它。

**判定非串行：** 骨架按数组顺序，第一站无 `depends_on`（或空），其后每一站的 `depends_on` 恰好是前一站。任一站多前置、跳步、或两个站依赖同一前驱（分叉），即非串行。

**本期行为：**

| 场景 | 行为 |
|---|---|
| 新建 | 只写串行：`depends_on` = 上一站 |
| 编辑非串行模板 | 可打开看队列（按数组顺序），顶栏说明「此模板含并行依赖，本期不能在此保存骨架」。主按钮对 spec 禁用；名称/描述仍可 `PATCH` |
| 复制非串行源 | 不进「复制现有模板」下拉（只列可被本编辑器完整往返的 active 串行模板），避免副本被默默拉直 |

并行编辑器作为后续阶段单独开：先定「用户怎么说清谁可以同时开」，再改 UI，而不是在串行页上叠菱形。

## 8. 「升版」还要不要——结论

**产品面去掉；存储面保留。**

版本表的用处不是运营翻 v1/v2，而是：`PlanRevisionPayload` 钉 `template_key` + `template_version`，进行中计划仍解析得到当时 spec；新需求用新的 `active_version`。`PATCH` 只能改名称/描述/启停，**不能原地改 spec**。

若改成真·覆盖 spec 且删历史行：进行中计划的 version 指针会悬空，规划回放/校验会坏。这不是 UI 文案问题。

落地：

- 列表「升版」→「编辑」。
- 展开区「版本历史」可保留为审计旁路（vN · 相对时间 · 当前），不作为作者主路径。
- 保存更改 = `POST /versions`（用户无感知）。不必做「被 N 个项目绑定」提示：下一单新规划用新 spec，钉住的旧计划不受影响。

## 9. 未决

本期拍板已收口（§0）。并行骨架的产品形状留到下一阶段再开，不在本稿展开。

## 10. 分期与验证

| 阶段 | 内容 |
|---|---|
| P0 | composer 出口勾选映射 + 单测；新建全页；列表新建改 Link；创建弹窗退役 |
| P1 | 编辑页（保存更改）；列表去掉升版话术；概览条；复制仅 active **且串行** 的模板；非串行打开只读骨架（§7.1）；离开保护 |
| P2 | 升版弹窗删除 |

验证必须含跨面：

- 词表无 active 角色 → 创建页不能保存，有去词表的入口。
- 保存含「诊断」两站的模板 → 角色词表该行 references 出现此模板。
- 发起页出现新模板卡片（名称/描述）；选中后编制区按新席位要人；缺编则就绪度「缺 …」。
- 提交需求 → 确认卡交付出口集合 = 勾选的收口（自定义 label 优先，否则站名）。
- 保存更改后：已钉住的旧计划 `template_version` 不变；新需求用新收口。
- 打开种子 `software_delivery` 编辑页：不能保存骨架；规划图仍为审查 ∥ 测试，不被拉直。

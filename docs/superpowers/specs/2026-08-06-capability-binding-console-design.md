## 1. 为什么要做

后端把「场地供给」这一层建起来了，但**人现在没有任何界面能配它，也看不见它生效与否**。具体三个洞：

1. **配不了**：项目技能/MCP 绑定只有 API，没有入口。
2. **看不见为什么没生效**：员工带的技能若被限定到别的项目，进本项目会被静默过滤掉（这是设计要的隔离）。但员工配置页只显示"该员工有哪些技能"，不显示"哪些技能只在某些项目生效"——用户会得到「我明明绑了，为什么没用上」的黑盒体验。这与当年 `project_placements` 那个"绑了没效果"的误导交互是同一类坑。
3. **技能详情页的文案现在是错的**：`skills/detail.tsx:354` 写着「依赖只做装载校验……**依赖不会自动为员工开通能力**」。依赖闭包落地后，env 已配齐的依赖**会**被自动补进投影（`source=dependency_closure`）。文案必须跟着改，否则是明确的误导。

## 3. 页面一：项目配置页「能力绑定」tab（P0，必须）

### 3.1 落点

`project-config-page.tsx` 新增第五个 tab：

```tsx
<ProjectConfigTab value="capabilities">能力绑定</ProjectConfigTab>
```

放在「剧本编制」之后、「协调策略」之前——编制回答"谁来干"，能力绑定回答"这块场地提供什么"，两者都是执行前置，相邻更符合心智。归档项目 `disabled`（沿用现有 `configFieldsDisabled`）。

### 3.2 结构：一个 tab、两个区

**不拆成两个 tab**。用户心智是"这个项目提供什么能力"，技能与 MCP 是同一件事的两种形态。

```
能力绑定
├── 说明条（常驻，非 dismissible）
│   「这里绑定的能力对进入本项目的所有数字员工生效，且只在本项目的任务中投影。
│     员工自带的通用能力不受影响。」
├── 区一：项目技能
│   列表（技能名 / slug / 风险等级 / 依赖 MCP 数 / 移除）
│   + 从技能市场添加（Select，排除已绑定）
│   + 依赖闭包预览（见 §3.4）
└── 区二：项目 MCP
    列表（服务名 / server_key / transport / 凭据 env 变量名 / 移除）
    + 从注册表添加（Select，排除已绑定）+ 可选凭据 env 输入
```

两区各自独立草稿态与保存按钮（分别对应两个 PUT 端点），不要合并成一次提交——它们是两个声明式全量替换，混在一起会让"部分失败"无法表达。

### 3.3 交互（两区一致，复用 05567dec 的形态）

- 本地草稿态：改动后出现「未保存」pill + 全量替换语义 Alert（「保存将以当前列表整体替换该项目的绑定」）
- 「保存绑定」→ 声明式 `PUT {items:[...]}`
- 保存失败 → Alert 直接呈服务端 message（含点名的 server_key）
- 四态齐：loading / empty / error / 保存失败
- 后台刷新时**保留现有数据**，不得卸载主体内容（`DESIGN.md` 工作对象界面规则）

### 3.4 依赖闭包预览（本页的关键增量）

添加一个技能到草稿时，若该技能 `runtime_dependencies.mcp_servers` 非空，**在该行下方展开一条提示**：

> 该技能依赖 `github-mcp`、`db-mcp`：任务派发时会一并投影（若执行者已配齐所需环境变量）；未配齐则该次派发会被拦下并提示补齐。

数据前端自己算，**不需要新端点**——`Skill.runtime_dependencies.mcp_servers` 已随技能列表返回。

这条提示是本页最有价值的部分：它把 §4.3 那条"闭包必须跟着走、但只补 env 已满足的"规则**在配置时就讲清楚**，而不是等派发失败了再让人去猜。

### 3.5 权限

项目负责人即可操作（三层模型决策 10），无需额外前端判权——后端 `project.config.edit` 已把关，403 时呈服务端消息即可。

## 4. 页面二：员工配置页的场地可见性（P1，必须）

### 4.1 落点

`employee-capabilities-panel.tsx` 的「已生效技能」列表（约 262 行起）。

### 4.2 改动

每个技能行按 `Skill.project_bindings` 追加一个标记：

| project_bindings | 标记 | 悬浮/副文案 |
|---|---|---|
| 空 | 「通用」 | 该技能在所有项目的任务中都会投影 |
| 非空 | 「限 N 个项目」 | 列出项目名（`project_name` 已随字段返回，**不要裸 UUID**） |

标记用 `StatusPill`，通用态 `tone=neutral`、限定态 `tone=info`。

### 4.3 为什么必须

没有它，「员工带着 B 项目的技能进 A 项目 → 不投影」这条**设计上正确**的行为，在界面上表现为"绑了没生效"。这是本次三层模型最容易被误解成 bug 的地方，也是唯一一处用户能感知到场地过滤的位置。

同一处的「个人 MCP」区照同样规则加标记（`McpServer.project_bindings`）。

## 5. 页面三：技能详情页（P1，小改但必须）

### 5.1 文案纠正（承重）

`skills/detail.tsx:354` 现文案：

> 依赖只做装载校验：员工执行任务时若未绑定所依赖的 MCP（或缺环境变量），派发会被阻断等待人工处理；**依赖不会自动为员工开通能力**。

加粗那句在依赖闭包落地后**不再准确**。改为：

> 依赖分两种情况：所依赖的 MCP 已在注册表中、且执行者已配齐它要求的环境变量时，派发会**自动把它一并投影**（记为 `dependency_closure`，可在派发记录中追溯）；若环境变量未配齐，派发会被阻断等待人工处理——**依赖永远不会替员工开通缺失的凭据**。

这条纠正比页面上任何新功能都重要：错误文案会让人对"为什么这个 MCP 自己出现了"产生错误心智模型。

### 5.2 引用面（可与 5.1 同批，成本很低）

顶部 MetricCard 行（`detail.tsx:195-199` 现有「团队安装」「数字员工安装」）加第三张：**「项目绑定」= `skill.project_bindings.length`**；下方绑定列表加一个「项目绑定」分组，形态直接抄现有的团队/员工两组。

作用：停用或删除技能前看得见影响面——与收口批做的角色词表 `references` 是同一个模式。

## 9. 风险

| 风险 | 缓解 |
|---|---|
| 两区共用一个保存按钮 → 部分失败无法表达 | §3.2 明确各自独立提交 |
| 全量替换语义被误解成增量添加 → 用户少填一项就清掉别人的绑定 | 常驻 Alert + 「未保存」pill + U2 断言 |
| 闭包预览让人以为"绑了技能就自动有凭据" | §3.4 文案必须带"若执行者已配齐所需环境变量"这半句；§5.1 同源纠正 |
| 复原 05567dec 的面板时把已删的旧 API 一起带回来 | 只抄 UI 形态，端点用 §0.0 列的当前契约 |
| 项目名缺失导致裸 UUID | `project_bindings` 已带 `project_name`；缺失时降级为「未命名项目 (前 8 位)」，不得裸 UUID |

## 10. 一句话方案

> **项目配置页给场地供给一个配置入口（两区、声明式全量替换、绑定时就把依赖闭包讲清楚），员工页与技能页把"这条能力在哪些场地生效"显性化——让本来正确的场地过滤不再被误读成"绑了没生效"。**

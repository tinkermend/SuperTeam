# 团队管理首页与新建团队闭环优化设计

日期：2026-06-25
> 复核状态：06-25团队创建页面优化
状态：已确认，待实现计划

## 1. 背景

团队管理首页和新建团队页已经具备基础能力，但当前体验与产品语义有几处偏差：

- 团队首页卡片描述文字可能溢出，卡片信息层级不稳定。
- 团队首页把团队状态、团队类型等概念放在视觉重点中，但当前团队管理更应表达团队组织事实和数字员工归属，不应把数字员工运行状态混入团队卡片。
- 新建团队页的图标选择过少，布局不友好，且图标与颜色耦合。
- `团队标识 slug` 文案暗示自动生成，但用户仍需要填写，且规则不清楚。
- 新建团队的负责人应从平台注册的人类用户中选择；团队内员工应是数字员工，不应继续用人类普通成员/观察者列表承载。
- 创建团队时选择数字员工只应展示未归属团队的数字员工；已归属任何团队的数字员工不应出现在候选列表中。

本设计基于 `docs/design/teamManager/` 下三张参考图，但只采纳当前平台真实具备或本次可最小补齐的能力。图片中平台没有的字段和按钮不纳入实现。

## 2. 目标

- 优化团队首页卡片，解决长描述溢出，保留高密度且可扫读的信息结构。
- 新建团队页采用更清晰的身份、负责人、数字员工、确认流程。
- 团队负责人从平台注册人类用户列表选择。
- 团队数字员工从未归属数字员工池选择。
- 创建团队提交时将选中的未归属数字员工绑定到新团队。
- 前后端同时校验 `slug` 只允许英文 URL 标识。
- 保持现有团队、人类用户、数字员工模型，不做完整团队成员体系重构。

## 3. 非目标

- 不引入团队类型字段。
- 不在团队首页展示团队运行状态。
- 不把数字员工运行状态、Runtime 状态或 Provider 状态混入团队卡片。
- 不展示已归属其他团队的数字员工，也不做灰色禁用候选项。
- 不重构统一团队成员体系，不把人类用户和数字员工合并进同一成员表模型。
- 不实现新建用户、邀请用户、数字员工创建向导或 Runtime 绑定能力。
- 不改项目成员池、任务分派、OpenFGA 或 Runtime/Provider 协议。

## 4. 领域模型口径

本次沿用现有模型：

- 团队负责人是人类用户，由 `human_owner_user_ids` 表达。
- 数字员工是独立执行身份，由 `digital_employees.team_id` 表达团队归属。
- 一个数字员工只能归属一个团队。
- `tenant_team_members` 仍表示人类团队成员，不作为本次新建团队页的主要成员选择对象。
- 团队首页的 `digital_employee_count` 是数字员工归属数量，不代表运行状态。

因此，本次需要补齐的是团队创建流程中的数字员工归属写入能力，而不是重做成员体系。

## 5. 团队首页设计

### 5.1 信息结构

首页保留 `/teams` 现有页面入口和主操作。卡片采用参考图 1 的目录型结构，但收敛字段：

- 团队图标。
- 团队名称。
- 团队描述，两行以内截断，不允许溢出卡片。
- 负责人摘要，展示人类负责人头像、名称和次级信息。
- 数字员工数量。
- 代表数字员工头像或紧凑列表。
- 详情入口。

不展示：

- 团队类型。
- 团队运行状态。
- 与数字员工运行态相关的状态标签。

如果当前接口没有团队描述字段，卡片描述使用团队 metadata 中已有可解释描述；若没有描述，展示低权重占位文案，例如 `暂无团队描述`，不伪造业务内容。

### 5.2 布局规则

- 卡片高度保持稳定。
- 描述区域固定最大两行并使用 `line-clamp`。
- 负责人和数字员工摘要使用固定行高，避免头像数量变化造成卡片抖动。
- 空状态、加载态、错误态继续使用项目级 v3 组件。
- 搜索和筛选只保留现有真实字段，不新增团队类型筛选。

## 6. 新建团队页设计

### 6.1 页面结构

新建团队页采用独立页面结构，参考图 2 和图 3 的组合：

- 顶部标题与面包屑。
- 步骤区：团队身份、负责人和数字员工、确认创建。
- 右侧或顶部摘要区展示团队名称、slug、图标、负责人和已选数字员工数量。
- 底部操作区提供取消、上一步、下一步或创建团队。

不新增图片中的团队类型字段。

### 6.2 团队身份

字段：

- 团队名称：必填，用于页面展示。
- 团队标识：必填，只允许英文 URL slug。
- 团队图标：从 lucide 图标库中选择。
- 团队颜色：从项目允许的色调中选择。

slug 规则：

- 长度 3 到 64 个字符。
- 只允许小写英文字母、数字和连字符。
- 必须以英文字母开头。
- 不能以连字符结尾。
- 不能包含中文、空格、下划线或其他符号。
- 示例：`platform-dev`、`security-audit`。

自动建议规则：

- 英文团队名称可自动转为小写 kebab slug。
- 中文团队名称不直接生成中文 slug。
- 如果名称无法生成合法英文 slug，展示空 slug 和明确提示：`请填写英文标识，例如 platform-dev`。
- 用户手动编辑 slug 后，不再被团队名称变化覆盖。

前端做即时校验，后端做最终校验和唯一性校验。

### 6.3 图标库

图标选择参考图 2，但实现必须使用项目可维护方式：

- 图标来源使用 `lucide-react` 或当前已引入的 lucide dynamic icon 能力。
- 默认展示一组精选图标。
- 支持搜索全部可用 lucide 图标。
- 图标选择和颜色选择解耦。
- 已选图标在预览区实时展示。

后端 metadata 继续保存 `display.icon_key` 和 `display.color_tone`，不引入新的团队类型字段。

### 6.4 团队负责人

负责人从平台注册用户中选择：

- 数据源复用现有用户列表或搜索接口。
- 只展示 active 用户。
- 选择后展示紧凑负责人卡片，包括头像、名称、邮箱或用户名、`人类用户` 标识。
- 负责人不进入数字员工列表。

后端仍要求至少一个 `human_owner_user_ids`。

### 6.5 团队数字员工

数字员工选择参考图 3，但修正业务口径：

- 候选列表标题为 `可加入的数字员工`。
- 只展示未归属团队的数字员工，即 `digital_employees.team_id IS NULL`。
- 已归属任何团队的数字员工不展示。
- 不做已归属员工的禁用态，也不展示灰色行。
- 候选项展示数字员工头像、名称、角色、描述摘要、风险等级或基础状态字段。
- 右侧或下方展示 `本团队数字员工` 已选列表，可移除。
- 已选数字员工不能重复加入。

如果没有未归属数字员工，展示空状态：`暂无未归属数字员工，可先到数字员工页面创建或释放归属。`

## 7. 后端接口设计

### 7.1 查询未归属数字员工

扩展现有数字员工列表接口：

```text
GET /api/v1/digital-employees?assignment=unassigned&status=&limit=&offset=
```

规则：

- `assignment=unassigned` 表示只返回 `team_id IS NULL` 的数字员工。
- 继续支持现有 `team_id=<uuid>` 查询团队内数字员工。
- `assignment=unassigned` 与 `team_id` 同时出现时返回 400，避免语义冲突。
- 响应仍使用现有 `DigitalEmployee` 结构。

前端也可以在第一版使用 `GET /api/v1/digital-employees/overview` 扩展同等过滤，但推荐优先扩展列表接口，因为新建团队只需要候选列表，不需要完整运行工作台聚合。

### 7.2 创建团队并绑定初始数字员工

扩展 `POST /api/v1/teams` 请求体：

```json
{
  "name": "研发智能体团队",
  "slug": "ai-research-team",
  "human_owner_user_ids": ["..."],
  "initial_digital_employee_ids": ["..."],
  "metadata": {
    "display": {
      "icon_key": "users-round",
      "color_tone": "blue"
    }
  }
}
```

后端事务规则：

- 创建团队。
- 校验负责人是当前租户 active 人类用户。
- 校验 slug 合法且唯一。
- 校验每个 `initial_digital_employee_ids` 属于当前租户。
- 校验每个选中数字员工 `team_id IS NULL` 且未删除。
- 在同一事务中将这些数字员工 `team_id` 更新为新团队 ID。
- 如果任一数字员工已被其他并发请求绑定，则整个创建失败并返回可解释错误。
- 写入审计事件，记录绑定的数字员工数量和 ID 列表。

`initial_members` 保留兼容现有接口，但新建团队页面本次不再使用人类初始成员选择。

### 7.3 slug 校验

后端在创建和更新团队时统一校验：

```text
^[a-z][a-z0-9-]*[a-z0-9]$
```

长度统一为 3 到 64 个字符；前端即时提示，后端最终拒绝不符合长度或格式的值。

错误信息应能区分：

- slug 格式不合法。
- slug 长度不合法。
- slug 已存在。
- 数字员工已归属其他团队。
- 数字员工不存在或无权限。

## 8. 前端数据流

团队首页：

- `GET /api/v1/teams` 获取团队摘要。
- 对每个团队按现有方式获取代表数字员工，或在不扩大接口的前提下降低代表展示数量。
- 卡片渲染只使用真实返回字段和 metadata。

新建团队：

- `GET /api/auth/users?q=&status=active` 获取负责人候选。
- `GET /api/v1/digital-employees?assignment=unassigned&limit=&offset=` 获取未归属数字员工候选。
- `POST /api/v1/teams` 提交团队名称、英文 slug、负责人、初始数字员工 ID 和 display metadata。
- 创建成功后跳转团队详情或返回团队列表，并刷新团队 summary。

## 9. 错误处理

- slug 不合法时，在字段下方即时提示。
- 未选择负责人时禁止提交。
- 未选择数字员工允许创建团队，但摘要显示 `0 位数字员工`。
- 未归属数字员工候选加载失败时，只阻断数字员工选择区，不影响身份和负责人填写。
- 提交时如果后端返回数字员工已被绑定，保留当前表单并提示刷新候选列表。
- 创建成功后清理表单状态。

## 10. 测试计划

后端测试：

- `listDigitalEmployees` 支持 `assignment=unassigned`。
- `assignment=unassigned` 与 `team_id` 同时传入返回 400。
- 创建团队时可以绑定多个未归属数字员工。
- 创建团队时拒绝已归属其他团队的数字员工。
- 创建团队时拒绝非法 slug。
- 创建团队失败时不产生半绑定数字员工。

前端测试：

- 团队首页长描述不会溢出。
- 团队首页不渲染团队类型和团队状态标签。
- 新建团队 slug 只接受英文 slug。
- 中文团队名不会生成中文 slug，并提示用户填写英文标识。
- 负责人搜索使用人类用户。
- 数字员工候选请求携带 `assignment=unassigned`。
- 已选数字员工提交为 `initial_digital_employee_ids`。
- 数字员工候选为空时展示正确空状态。

局部验证：

- `corepack pnpm --filter ./apps/web run test`
- 相关 Go 单元测试。
- `git diff --check`

真实链路验证：

- 启动或确认 Web 和 Control Plane 运行。
- 访问 `/teams/new`。
- 输入中文团队名称并填写英文 slug。
- 选择一位人类负责人。
- 仅看到未归属数字员工候选。
- 创建团队成功后确认团队详情和团队首页数字员工数量更新。
- 验证已归属其他团队的数字员工不会再次出现在新建团队候选列表。

## 11. 实施边界

本设计确认后，下一步只进入 implementation plan。实施计划应保持最小闭环，不把完整团队成员体系重构、数字员工创建向导、团队类型、团队状态面板或 Runtime/Provider 状态展示纳入同一次任务。

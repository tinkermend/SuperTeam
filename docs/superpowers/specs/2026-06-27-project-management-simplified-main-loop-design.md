# 项目管理主闭环简化设计

日期：2026-06-27
状态：已确认，待实施计划

## 1. 背景

当前项目管理已经具备 Project、ProjectDemand、PlanRevision、ProjectTask、DecisionRequest、ExecutionSummary、事件流、证据、预算和归档等底层能力，但前后端默认体验过度暴露内部协调对象。项目负责人打开项目管理时，需要同时理解 coordination job、route decision、dispatch gate、execution trace、budget ledger、archive snapshot 等技术事实，主业务闭环被淹没。

本设计将项目管理重新收敛为一条主路径：

```text
任务发起 -> Plan 编排 -> 数字员工执行 -> 负责人审批/补证/验收 -> 结果关闭
```

底层能力不删除，但必须从项目管理默认视图降级到高级入口、推进详情或平台管理视图。

## 2. 目标

- 让项目管理默认服务项目负责人日常工作，而不是成为所有项目底层对象的调试台。
- 将人类员工角色收敛为平台管理员、项目负责人、团队负责人。
- 支持一个项目有一个或多个项目负责人，一个团队有一个或多个团队负责人。
- 多负责人场景采用“任一负责人处理即生效”，并记录实际处理人。
- 将项目服务池作为项目调用数字员工的核心产品概念。
- 让任务发起成为唯一提交需求入口。
- 将 Plan、执行、审批、补证、最终结果串成用户可理解的闭环。
- 用业务聚合 API 减少前端从大量底层接口拼装页面含义。

## 3. 非目标

- 不删除现有 RouteDecision、CoordinationJob、DispatchGate、ExecutionTrace、Budget、Archive 等底层能力。
- 不引入调试者、审计员、验收人、reviewer、leader 等新的一等人类角色。
- 不在第一阶段重写 Temporal 项目协调、Runtime 分派或 Provider 执行协议。
- 不在第一阶段实现复杂多人会签规则。
- 不把数字员工建模成人类员工角色。
- 不让普通项目管理主页面默认展示所有高级对象。

## 4. 人类角色模型

系统里的人类员工只暴露三个业务角色。

### 4.1 平台管理员

平台管理员负责平台级配置和异常处理：

- 人类员工管理。
- 团队管理的全局权限边界。
- 数字员工创建和全局治理。
- Runtime、Provider、能力注册、连接器和平台健康。
- 平台级权限、资源、配置缺失等问题。

平台管理员不参与普通项目的日常 Plan 确认、执行审批或最终结果判断，除非问题属于平台资源或权限层。

### 4.2 团队负责人组

一个团队可以有一个或多个团队负责人。团队负责人组负责团队数字员工供给侧：

- 管理团队数字员工池。
- 判断团队数字员工能力和可用状态。
- 决定是否允许某个项目调用本团队数字员工。
- 处理跨项目调用授权、团队资源约束和供给侧风险。

团队负责人组收到授权待办时，任一团队负责人处理即生效。

### 4.3 项目负责人组

一个项目可以有一个或多个项目负责人。项目负责人组负责项目需求侧和最终业务闭环：

- 项目目标和问题场景。
- 项目服务池。
- Plan 确认。
- 高风险动作审批。
- 补充信息和补证判断。
- 最终结果接收。
- 项目或需求关闭。

项目负责人组收到项目待办时，任一项目负责人处理即生效。

### 4.4 数字员工

数字员工不是人类角色，而是可调度执行身份。数字员工归属团队，具备能力、工具、Runtime/Provider 绑定、权限范围和状态。项目通过项目服务池调用数字员工。

## 5. 主业务闭环

主闭环固定为：

```text
任务发起
-> 选择项目
-> 写入 ProjectDemand
-> 项目协调线程生成 Plan
-> 必要时项目负责人组任一人确认 Plan / 补充信息 / 授权高风险动作
-> Plan 分解为 ProjectTask
-> 调度项目服务池里的数字员工执行
-> 结果结构化回写
-> 必要时项目负责人组任一人审批、补证或要求重做
-> 生成最终结果
-> 项目负责人组任一人确认关闭
```

关键规则：

- 任务发起是唯一提交需求入口。
- ProjectDemand 是用户提出需求的事实源。
- Plan 是面向项目负责人可理解的业务计划。
- ProjectTask 是系统内部执行任务，普通用户不直接创建。
- 项目服务池展示项目当前可调用的数字员工，数字员工来源团队和授权状态作为附加信息。
- 审批默认回项目负责人组。
- 跨团队调用数字员工的授权回团队负责人组。
- 平台级资源、Runtime、Provider、权限或能力注册问题回平台管理员。
- 多负责人处理动作时，任一负责人处理即生效，并记录实际处理人、时间、意见和关联对象。

## 6. 前端信息架构

一级入口收敛为五类。

### 6.1 工作台

工作台是当前登录人待办入口：

- 项目负责人待确认。
- 团队负责人待授权。
- 平台管理员待处理。

工作台不替代项目详情，它回答“我现在需要处理什么”。

### 6.2 任务发起

任务发起是唯一提交需求入口：

- 选择项目。
- 输入需求。
- 提交 ProjectDemand。
- 跳转到本次需求推进详情。

用户不需要理解 Runtime Task、ProjectTask 或 Workflow Instance。

### 6.3 项目管理

项目管理采用项目负责人视角。默认只展示：

- 项目目标。
- 项目负责人组。
- 项目服务池。
- 当前需求、当前 Plan、执行状态。
- 待项目负责人处理动作。
- 最新结果和关闭动作。

项目管理首页不默认展示 coordination job、dispatch gate、execution trace、budget ledger、archive snapshot 等底层对象。

### 6.4 团队管理

团队管理采用团队负责人视角。默认只展示：

- 团队负责人组。
- 团队数字员工池。
- 数字员工状态和能力摘要。
- 跨项目调用授权。
- 团队级资源约束。

### 6.5 平台管理

平台管理采用平台管理员视角。放置：

- 人类员工。
- Runtime。
- Provider。
- 能力注册。
- 系统配置。
- 全局权限。
- 平台健康。

### 6.6 高级能力归位

现有复杂能力保留，但不再污染项目管理主视图：

- PlanRevision 放在计划历史或高级入口。
- ProjectTaskGraph 放在需求推进详情或项目高级视图。
- DispatchGate 对普通用户翻译成业务阻塞原因，技术细节放高级入口。
- ExecutionTrace 包装为执行记录，默认折叠。
- Evidence、Artifact、Report 在主路径只展示最终结果和关键证据，完整列表放详情。
- Budget 和 Archive 不在项目管理首屏展示，归入平台管理、项目关闭流程或高级入口。

## 7. 后端领域模型收敛

后端不推倒重来。现有底层对象多数保留，但需要以业务主模型重新组织。

### 7.1 HumanEmployee

人类员工。可承担平台管理员、团队负责人、项目负责人职责。一个人可以同时拥有多个职责。

### 7.2 Team

数字员工组织池。核心字段是团队负责人组和数字员工列表。

### 7.3 DigitalEmployee

可调度执行身份。归属团队，具备能力、工具、Runtime/Provider 绑定和状态。

### 7.4 Project

项目是业务闭环容器。项目负责人不应只由单个 `human_owner_user_id` 表达，应升级为项目负责人组。项目不应在产品心智上强绑定单一主团队；更重要的是绑定项目服务池。

### 7.5 ProjectServicePool

项目服务池记录项目可调用的数字员工：

- 数字员工 ID。
- 来源团队。
- 授权状态。
- 授权人。
- 授权时间。
- 使用约束。
- 当前可用状态。

实现上可以复用或迁移现有 `project_members`，但产品概念必须叫项目服务池，不再让用户理解泛化 member。

### 7.6 ProjectDemand

用户发起的一次需求。任务发起入口只创建 ProjectDemand。

### 7.7 PlanRevision

针对 Demand 生成的计划。项目负责人组任一人可确认、要求修改或驳回。

### 7.8 ProjectTask

Plan 分解后的内部执行任务。普通用户不直接创建 ProjectTask。

### 7.9 HumanAction / DecisionRequest

所有人类待处理动作统一投影成业务待办：

- 项目负责人：确认 Plan、补充信息、批准高风险动作、确认最终结果。
- 团队负责人：批准项目调用本团队数字员工。
- 平台管理员：处理平台级资源、权限、Runtime、Provider 或能力注册问题。

## 8. API 收敛

新增或收敛业务聚合 API，减少前端拼装复杂度。

### 8.1 我的待办

```text
GET /api/v1/workbench/actions
```

返回当前登录人的所有待办，按其平台管理员、团队负责人、项目负责人职责过滤。

### 8.2 项目负责人主视图

```text
GET /api/v1/projects/{projectId}/workspace
```

返回：

- 项目基础信息。
- 项目负责人组。
- 项目服务池摘要。
- 当前需求。
- 当前 Plan。
- 执行摘要。
- 待处理动作。
- 最新结果。
- 关闭状态。

### 8.3 任务推进详情

```text
GET /api/v1/project-demands/{demandId}/progress
```

返回一次任务发起后的推进详情：

- Demand。
- Plan。
- 执行阶段。
- 数字员工任务摘要。
- 待处理动作。
- 最终结果。
- 关键证据。

### 8.4 团队服务池

```text
GET /api/v1/teams/{teamId}/service-pool
```

返回团队负责人视图：

- 团队数字员工池。
- 数字员工可服务项目状态。
- 待授权调用。
- 授权历史。

### 8.5 高级接口

现有 route decisions、coordination jobs、dispatch gates、execution trace、budget ledger、archive snapshot 等接口保留，但归为高级、内部或平台诊断型接口，不作为普通项目管理页面默认拼装来源。

## 9. 状态语言

主路径状态使用业务语言，不向普通用户暴露底层技术状态名。

| 状态 | 含义 |
| --- | --- |
| 待计划 | 需求已提交，等待系统生成 Plan。 |
| 待确认 | 需要项目负责人组任一人确认 Plan、风险动作、补充信息或最终结果。 |
| 执行中 | 数字员工正在处理。 |
| 等待团队授权 | 需要团队负责人组任一人允许调用团队数字员工。 |
| 等待平台处理 | Runtime、Provider、权限、能力注册等平台级问题需要平台管理员处理。 |
| 需补充信息 | 数字员工或 Plan 需要更多上下文。 |
| 已完成 | 最终结果已生成并被确认。 |
| 已关闭 | 项目或需求闭环结束。 |
| 失败/暂停 | 需要人类判断下一步。 |

## 10. 错误处理

- 项目负责人不看 `dispatch_gate.blocked` 等技术名，只看“缺少数据库读取权限”“目标数字员工不可用”“需要团队授权”等业务原因。
- 团队负责人只看供给侧问题：谁申请调用哪个数字员工、用途、期限、风险和约束。
- 平台管理员只看平台资源问题：Runtime 离线、Provider 不可用、能力未注册、权限配置缺失。
- 任一负责人处理生效，但必须记录实际处理人、处理时间、处理意见和关联对象。
- 如果项目负责人组或团队负责人组为空，这是配置错误，相关待办升级给平台管理员。

## 11. 分阶段实施

### 阶段 1：模型命名与主视图收敛

目标是不大动数据库，先把用户看到的概念改对。

- 项目管理主页面改成项目负责人工作台。
- 隐藏或折叠高级对象。
- 将 members 在 UI 上拆成项目负责人组和项目服务池。
- 多项目负责人采用任一负责人处理即生效。
- 保留现有接口，但前端只展示主路径需要的聚合信息。

验收标准：用户打开项目管理后，不需要理解内部协调对象，只看到项目、服务池、当前计划、待处理和结果。

### 阶段 2：负责人组与权限动作统一

目标是把单人 owner 模型升级为负责人组。

- Team 支持多个团队负责人。
- Project 支持多个项目负责人。
- 待办分发给负责人组，任一人处理即完成。
- `leader`、`reviewer`、`acceptance` 不作为一等人类角色展示。
- 审批记录保存实际处理人。

验收标准：多个项目负责人中任一人能确认 Plan、审批和确认结果；多个团队负责人中任一人能批准团队数字员工被项目调用。

### 阶段 3：业务聚合 API

目标是减少前端拼装复杂度。

- 新增 `/projects/{id}/workspace`。
- 新增 `/project-demands/{id}/progress`。
- 新增 `/workbench/actions`。
- 新增 `/teams/{id}/service-pool`。
- 默认页面改用聚合 API。

验收标准：项目管理页不再并行拉大量项目接口；主页面由少数业务聚合 API 支撑。

### 阶段 4：高级能力归位

目标是把历史复杂能力放回正确位置。

- 计划历史、任务图、执行记录进入需求详情或高级折叠区。
- 预算、归档、平台健康进入平台管理或项目关闭流程。
- 跨团队调用进入团队负责人授权视图。
- Runtime/Provider 问题进入平台管理员待办。

验收标准：复杂能力仍可追溯，但不再污染项目负责人主路径。

## 12. 验证策略

- 阶段 1 验证前端信息架构：项目管理主路径无内部对象泄漏，旧高级能力仍可访问。
- 阶段 2 验证多人负责人：任一项目负责人可确认，任一团队负责人可授权，非负责人不能处理。
- 阶段 3 验证聚合 API：页面查询数下降，数据和旧接口事实一致。
- 阶段 4 做真实闭环验证：任务发起 -> Plan -> 项目负责人确认 -> 数字员工执行 -> 最终结果 -> 项目负责人关闭。

所有涉及功能闭环的实现完成前，必须按项目规则使用真实 Web、Control Plane、数据库、Runtime 或 Provider 路径验证；不能用 mock、组件测试或单元测试替代真实链路结论。

## 13. 已确认决策

- 选择 C 方案：前后端一起重构一版最小闭环。
- 人类员工角色只暴露平台管理员、项目负责人、团队负责人。
- 项目负责人和团队负责人都可以有一个或多个。
- 多负责人场景采用任一负责人处理即生效。
- 不使用浏览器可视化辅助，本设计用文本确认。

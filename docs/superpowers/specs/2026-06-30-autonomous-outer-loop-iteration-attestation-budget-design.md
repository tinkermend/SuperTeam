# 自治外环 Spec 提纲：返工迭代 · 执行证明 · 预算熔断 · 结论复利

> 日期：2026-06-30
> 状态：提纲（待展开评审）
> 配套：本文是「执行基座」内环 spec（`2026-06-29-project-code-workspace-runtime-affinity-design.md`）的另一半。内环让多员工"能在真实代码/资源上跑、能交接"；外环让它"判断—返工—验收—回写"真正闭合且可信、可控、可复利。

## 0. 为什么需要这份

内环只闭合了「执行 + 交接」。若只做内环，系统是**强大但需贴身监护的工具**，不是自走系统，且存在三个致命隐患：① 流程是线性的（开发→审查→完成），现实是迭代的；② worktree 不等于"事情真发生了"（违背"不得把 mock 当真实链路"宪法）；③ 多员工在真实代码库上跑 = 真实算力/token/时间，无熔断即失控。本文给出补齐外环的四根支柱。

---

## 1. 支柱 A —— 返工迭代状态机（让线性变收敛）

**问题**：当前模型隐含"一次产出即完成"。真实是 开发→审查/测试**失败**→返工→再审→…→收敛。缺这条回路就没有自治。

**模型要点**
- 引入 **Work Item（工作项）** 作为"一个目标的收敛单位"，其下是多次 **Iteration（迭代）**；ProjectTask 是迭代内的一次执行。
- 协调线程（Temporal coordinator）跑收敛循环：
  ```
  dispatch 开发任务 → 产出交接单(branch/head/base)
    → dispatch 审查/测试任务（按交接单 ref）
    → 收集 verdict
    → 全 pass ? → 进人类验收
            : → 建返工任务（回到同一 branch/worktree/员工），
                把 reject 理由作为输入上下文 → 下一轮 Iteration
  ```
- **worktree/branch 必须跨迭代存活**，不在迭代间清理（接内环"工地生命周期绑任务终态而非进程退出"的洞 4）。
- 返工路由是一种 **RouteDecision**（复用现有 RouteDecision/ProjectTask/审计模型，不新造协作通道）。

**终止守卫（必须有，否则死循环烧钱）**
- `max_iterations` 上限。
- 预算上限触顶（见支柱 C）。
- **无进展检测**：同一失败重复 N 次 → 不再自旋，升级人类（区分"在收敛"与"在原地打转"）。
- 终态：`converged` | `exhausted` | `human_aborted`。

**输出**：Work Item 收敛历史（每轮 verdict、改了什么、为何收敛/放弃），是后续"结论回写"（支柱 D）的原料。

---

## 2. 支柱 B —— 执行证明 Attestation（让"跑过了"可验证）

**问题**：测试员产出"绿色报告"——如何确认它真的在真实 worktree 跑了，而非幻觉一份报告？worktree 给了真实环境，却没给"真实的证据"。这正是仓库既有的 evidence/acceptance 缺口。

**核心区分**
- **Agent 叙述**（"我跑了测试，通过了"）≠ **Runtime 证明**（在 commit `abc` 上 `pnpm test` 退出码 0，日志哈希 X）。
- **审查/验收判断的是 Attestation，不是叙述。**

**Runtime 每个任务捕获的结构化执行记录**（Runtime 持有 worktree，天然是证据源）
- 执行的命令 argv 列表 + 各自**退出码** + 时长。
- stdout/stderr 引用（落 logs，存哈希）。
- 产物哈希（测试报告/覆盖率/构建产物）。
- git 证据：diff、commit sha、branch、base ref。
- provider session id（可追溯到哪次会话）。

**契约约束（反幻觉的关键）**
- **verdict schema 必须引用 attestation**：一个"通过"的判断若没有可核验的执行记录支撑，**按契约即无效、自动驳回**。
- 这把宪法那条"不得把 mock/单测/构建当真实链路验证"**结构化落地**：绿灯必须挂在真实执行记录上。
- 测试任务尤甚：测试命令 + 退出码 + 覆盖率产物 = 证据，验收/审查可复核。

---

## 3. 支柱 C —— 预算熔断 + 人类审批吞吐（让自治可控、不被人卡死）

### C1 预算 / 熔断
- **多层预算**：项目级 + Work Item 级（token、墙钟时间、迭代次数、金额）。预算是你们模型里 Project 的既有聚合，本支柱把它**接到执行那一刻**。
- **派发时 + 执行中（心跳）双重校验**：触顶 → **暂停并升级人类**，不是静默继续。
- 收敛循环（支柱 A）把预算作为终止守卫之一。
- **失控检测**：无进展自旋、重复同一失败 → 跳闸。

### C2 人类审批吞吐（防止瓶颈从机器转移到人）
- **风险分级**：只读 / 低风险写 / 破坏性写 / 上线发布。**只有高档位才暂停等人类**；低档位走 Policy 自动放行。
- **批量与队列**：人类负责人看到的是**审批队列**而非逐条打断（衔接现有 `inbox-actionable-work-queue` spec）。
- **委托 Policy**：谁能批什么、Policy 包络内自动批。
- 目标：当 Agent 并行产能上升（N 项目 × M 员工），人类决策吞吐**随之扩容**，否则跃迁被未扩容的人类审批卡死。

---

## 4. 支柱 D（横切）—— 结论回写 / 复利（让组织变聪明）

**问题**：worktree 是 ephemeral，干完即拆。若经验不沉淀，每个项目从零开始 = 更快的重复劳动，不是能力增长。

**要点**
- Work Item 收敛后，**蒸馏结构化结论**（什么失败、什么修好、决策与理由）写入全局上下文 / 可复用知识存储，不随 worktree 销毁。
- 后续任务执行时，把相关历史结论作为**上下文切片**注入（接宪法"只注入当前任务需要的上下文切片；关键结论必须结构化回写"）。
- 这是"更快重复" → "组织复利"的转折点。

---

## 5. 与内环的耦合点

| 耦合 | 内环提供 | 外环依赖 |
|---|---|---|
| worktree 跨迭代存活 | 工地生命周期绑任务终态（洞 4） | 返工迭代复用同一 branch/worktree |
| 执行证明 | Runtime 持有 worktree、捕获命令/退出码/产物 | Attestation 的证据源 |
| 交接单血缘 | 开发产出 branch/head/base | 收敛循环按 ref 派审查、按理由派返工 |
| 预算 | 执行槽位、心跳 | 熔断在执行中校验、迭代守卫 |

---

## 6. 落地分期（建议）

- **Phase 1（与内环并行最小闭合）**：① 收敛循环的"驳回即返工"最简版（max_iterations + 无进展升级）；② 执行证明的最小集（命令 + 退出码 + commit sha + 日志哈希）+ verdict 必须引用 attestation 的契约约束。这两条直接补上"线性"和"不可信"两个致命隐患。
- **Phase 2**：风险分级 + 审批队列 + 委托 Policy；多层预算与失控检测。
- **Phase 3**：结论蒸馏与复利、上下文切片回注。

## 7. 待决策项

1. Work Item / Iteration 是否进核心模型，还是用 ProjectTask + 标签 + RouteDecision 组合表达（倾向后者，避免新封闭枚举）。
2. Attestation 的存储与可信边界：Runtime 自证是否足够，还是需要不可篡改记录（签名/哈希链）。
3. 风险分级表与自动放行 Policy 的归属（Tenant Profile / Policy）。
4. 无进展检测的判定信号（相同失败指纹？覆盖率/diff 无变化？）。

---

## 8. 一句话定位

内环让系统**能跑**；本外环让它**闭合、可信、可控、可复利**。两者缺一，跃迁不成立：只做内环是"通而不闭"，只做外环是"无处落地"。

## 9. 跨 spec 已知缺口（本设计明确不覆盖，勿默认已设计）

> 与内环 spec（`2026-06-29-project-code-workspace-runtime-affinity-design.md` §12）共享本清单。两份 spec 都偏「代码交付 + 乐观路径」思维，下列项是两份共同的盲区，列出以划清边界——实现者不得默认它们已被设计。每项均为**独立专题，待立项**。

1. **验收标准 / 意图规格（最大语义空洞）**：本外环讲了"全 verdict pass → 验收 → 收敛"，但未定义"acceptance criteria 从哪来、怎么流到审查/测试员"。无意图规格则支柱 B 的 attestation 与支柱 A 的"收敛"皆悬空——证明"真的跑了"≠"做对了目标"。**直接威胁外环存在意义，应最优先。**
2. **Agent 执行隔离 + 密钥泄漏**：共享 Runtime 节点跑近乎不可信 agent 代码，沙箱模型未设计；MCP/git 密钥真实值注入进程环境后可被 agent 读取外泄，密钥生命周期未设计。
3. **非 git 副作用（数据库/迁移/外部调用）**：worktree 只隔离代码；有状态、不可回滚副作用未纳入 attestation/预算/熔断。关联宪法「删除写入、迁移、上线发布为高风险」。支柱 B/C 当前只覆盖 git 与命令退出码，未覆盖外部状态。
4. **崩溃恢复与幂等**：节点半途崩溃后的恢复语义、有副作用步骤的幂等性（at-least-once vs exactly-once）未答；影响支柱 A 迭代重入与支柱 B attestation 完整性。
5. **人类飞行中可观测性 + 多分支并行收敛**：① attestation 事后，缺实时观测/中途叫停（与「人类决策一等」相悖）；② 支柱 A 迭代状态机隐含单分支，多分支并行→集成→整体收敛未建模。

> 处置建议：#1 与 #3 优先立独立专题；其余随实现阶段补。本 spec 的假设前提显式声明为「目标已定义、产出为代码分支、执行环境可信且成功」。
> 进度：**#1 已立项** → `2026-06-30-intent-acceptance-criteria-design.md`（意图层，定义收敛目标，被本外环支柱 A/B 消费）。#2/#3/#4/#5 待立项。

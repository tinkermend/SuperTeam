  4. 策略与场景模板（剧本）结合：剧本承载自治姿态（默认档 + 上限档），自动化规则在剧本上限内选档；**不做 skill/MCP 独立风险标签体系**，差异化由剧本承担

  6. P2 自治档位缺省 = **遇闸暂停**；「完全自动化」须显式选择
  7. 项目级策略上限落在 **`coordination_policy.autonomy_ceiling`**（§5.7）
  8. 策略变更权限：最低 **项目负责人**；租户管理员同样可改

## 1. 背景与问题

### 1.1 三条调用面共用一条执行底盘

平台上「让数字员工干活」目前有三条入口，共用同一条执行底盘（员工 + 项目锚 + 能力投影 + Runtime）：

| 调用面 | 现状入口 | 人在不在场 |
|---|---|---|
| 交互 Chat | 任务中枢对话模式（`run_kind=chat`，项目锚，线程恢复） | 在 |
| 自动化 | `internal/automation/`（规则支持 plan/loop/chat 三模式，`scenario_template_key` 已在规则上） | 不在 |
| 外部 API | 规划中（能力外放给其他系统程序化调用） | 不在 |

### 1.2 三个治理缺口

**缺口一：Chat 旁路可动真格，但没有第二道能力面闸。**
三模式 spec §11 已拍板「chat run 以员工完整常备权限执行（全速档），打字者即授权人」，否决了四层只读方案；兜底是产出隔离（quarantined）+ 全量审计。但产出隔离管的是**业务效力**（不进证据链/协调/验收），管不住**真实副作用**（改仓库、调 MCP、写外部系统）。Chat 因此成为「控制平面管得到任务轨、管不全对话轨」的洞。

**缺口二：「审批」一词被过载，导致自动化与外放无从设计。**
自动化必须静默执行、外部 API 必须可编程调用——若把人类审批串进这两条路，功能即失去意义；若因此完全放弃治理，又违反宪法「不得让数字员工绕过人类决策」。症结是把三个正交概念揉成了一个词（§2）。

**缺口三：策略无载体。**
「哪类工作可以多自动」本质上是打法（剧本）的属性，但现状没有结构化承载：模板 spec 里的 `risk_policy`（如 `software_delivery` 的 `release_requires_human: true`，见 `058_scenario_templates.sql` 种子数据）是雏形，未与闸点 resolver 打通。

### 1.3 历史教训（不得重演）

- **`approval_policy` 之死**（CHANGELOG 2026-07-22，spec `2026-07-22-project-dead-policy-retirement.md`）：项目级 `approval_policy`/`evidence_policy` 先造配置字段、始终无消费者，沦为误导用户的死面板，最终连表列带 UI 整体退役。→ 本方案的策略字段**天生有消费者**（§4.1 闸点清单是已实跑的代码），且分期要求「闸先于配置面」。
- **只读沙箱否决案**（tri-mode spec §11）：曾评审四层只读强制方案，因过度设计被否。→ 本方案不翻案：Chat 仍全速执行；补的是「能力面收窄 + 高危轻确认」，即对「打字即授权」的细化——**打字授权的是开跑，点头授权的是打开某类危险能力**。

## 2. 核心模型：三个正交概念 × 三个授权时刻

### 2.1 概念拆分

| 概念 | 是什么 | 发生时刻 | 适用 |
|---|---|---|---|
| **审批流** | 事中/事后人类决策：计划确认、验收、收件箱决策 | 执行期 | Plan / Loop 主轨 |
| **授权信封**（envelope） | 事先批过的能力预算：能用谁、哪些 skill/MCP、哪个项目、多大副作用面 | 配置期 | 全部三条调用面 |
| **交互确认** | 人正坐在屏幕前时的轻点头：打开高危技能、确认本轮动手 | 执行期（仅有人在场） | 仅交互 Chat |

**承重句：静默路径不是「无治理」，是「治理发生在配置时刻，而不是执行时刻」。** 这与 baseline 不变量 7 同构（automation 校验前移到规则保存时刻；运行期失效允许失败但必须通知）。

### 2.2 三条调用面的授权模型

```
                    ┌─ 交互 Chat ──── 授权时刻：打字时（+ 本轮高危轻确认）
  执行底盘  ←──────┼─ 自动化 ────── 授权时刻：保存/启用规则时
                    └─ 外部 API ──── 授权时刻：颁发凭据/绑定集成时
```

| | 交互 Chat | 自动化 | 外部 API |
|---|---|---|---|
| 运行期人类确认 | 可以有（轻确认） | **禁止** | **禁止** |
| 能力来源 | 项目 Chat 默认面 ∩ 本轮勾选 | 规则钉死的信封 | 集成/token 钉死的信封 |
| 出界行为 | UI 不可选 / 服务端拒 | 直接拒 + 告警 | 4xx 明确错误 + 审计 |
| 撞上 human 档策略 | 就地弹确认 | park 进收件箱 + 通知（plan/loop）；拒（chat 规则） | 拒（同步语义）；异步升级另行立项 |
| 产出效力 | 旁路（quarantined），显式晋升才进主轨 | plan/loop 进主轨；chat 规则旁路 | 按开通时选定的模式 |

**出界即拒，不变形为「转去审批」。** 拒绝是自动化/API 该有的语义；「先审再跑」是调用方自己的工作流，或显式走 Plan 路径。

### 2.3 效力规则独立于调用面

`run_kind=chat`（无论人点的、定时的、API 触发的）→ 产出默认不进审批/验收轨；进入主轨的唯一通道仍是显式晋升（转为任务 / 直接创建 plan|loop demand）。三模式 spec §5 的隔离不变量全部保留，本方案不动。

## 3. 能力信封（Envelope）

### 3.1 定义与合成

信封是**过滤器，不是供给源**。能力供给仍是三层模型（员工常备 ∪ 项目绑定，含依赖闭包与冲突留痕，`internal/capabilityprojection`）；信封在派发时对投影结果做交集收窄：

```
实际投影 = 三层供给结果 ∩ 调用面信封
  交互 Chat：信封 = 项目 Chat 默认面 ∩ 本轮用户勾选（不勾选 = 默认面全量）
  自动化：  信封 = 规则保存时钉死的 skill/MCP 集
  外部 API：信封 = 集成/token 绑定的 skill/MCP 集
```

### 3.2 挂点

| 信封 | 挂在哪 | 校验时刻 |
|---|---|---|
| 项目 Chat 默认面 | 项目配置（第一版可缺省 = 等于项目绑定全量，之后再收紧） | 配置保存时 |
| 本轮勾选 | CreateRun 请求新增「本轮选用 skill」参数（⊆ 允许集，服务端校验） | 发送时 |
| 规则信封 | automation 规则 | 规则保存时（与编制校验同时刻） |
| API 信封 | 集成/token 记录 | 开通/换发时 |

### 3.3 与手动技能选择的关系

终端斜杠触发技能的 Web 化：选技能 = 声明本轮能力面。底层仍是会话投影 `skills[]`，触发从文本协议变成显式控件；选择记进 run 元数据供审计回放。UI 形态见 UI 草稿（本文不展开）。

## 4. 策略闸（Policy Resolver）

### 4.1 闸点清单（已存在、已实跑，策略只换 resolver）

派发前门禁的七种人类动作（`predispatch_gate.go:31-39`）：

```
permission_approval / risk_approval / missing_context / tool_authorization /
runtime_recovery / budget_approval / replan_decision
```

加上协调轨的两个人类闸：**计划确认**（plan review；plan/loop 模式差异本身就是「补链要不要人批」的既有二值先例）与**验收**（acceptance）。全平台人类闸就是这张清单，策略的消费者即它们。

### 4.2 「自动审批」的正确定义

> **闸照触发、决策对象照产生，只是 `resolved_by` 从某个人变成 `policy:{rule_id|template_key}`。**

保住三件事：

1. **审计不缩水**：每次自动放行都有决策记录，能回答「为什么这个高危动作在凌晨三点跑了」——因为某人在某日签了这份策略。
2. **状态机唯一**：不为无人值守 fork 第二条管道。既有凭证机制天然兼容（`preDispatchRiskApprovalGranted` 认「已批准的 decision」，不区分谁批的，见 CHANGELOG 2026-07-20 风险审批修复）。
3. **随时可收紧**：改策略即可回到人批，代码路径零变化。

这也是宪法「人类不被绕过」的兑现方式：人类的决策发生在签策略那一刻。**因此策略本身是高权对象**：谁能设「全自动」、策略变更审计、角色门槛，与策略同批设计，不后补。

### 4.3 三档 resolver（拒绝橡皮图章）

| 档 | 语义 | 前提 |
|---|---|---|
| `auto` | 策略放行，产生决策记录 | 该闸有**机器可判定判据**，或后果被信封兜住 |
| `notify` | 放行 + 主动告警（事后人看） | 要知情不要阻塞 |
| `human` | 阻塞等人 | 判据无法机器化 |

**自动验收特别条款**：验收是「结果成为项目事实」的闸。其 `auto` 档必须定义为「机器判据全过才自动通过，任一不过升级 `human`」——判据绑定既有的任务结果契约（result contract）、交付物门禁、对抗性复核（adversarial review / autonomy posture）。无判据的无条件自动验收比没有闸更糟（给未经检验的产出盖合法章），**禁止**。

### 4.4 撞 human 档的降级（配置时可见，不是运行期意外）

- plan/loop 自动化：park 进收件箱等人 + 通知（复用 `automation_alert` 与收件箱机制），与「编制运行期失效 → 失败 + 通知」同构。
- chat 自动化 / 外部 API 同步调用：无「等人」语义空间，直接拒 + 明确原因。API 的异步升级（202 + 回查）是独立立项，第一版不做。

### 4.5 差异化从哪来（不做独立风险标签）

**第一版不引入 skill/MCP/Capability 注册表上的「风险标签」。** 自治松紧的差异化由场景模板（剧本）的 `autonomy_default` / `autonomy_ceiling`（及既有 `risk_policy` 扶正）承担——「这类仗允许多自动」是打法属性，不必再在每个技能上贴第二套风险词表，否则与剧本抢事实源、配置面翻倍。

闸点判定输入仍只允许服务端可判定的声明式事实（剧本姿态、信封内容、预算额度、既有门禁快照中的结构化字段）。**禁止**采用 planner/模型自报字段——门禁快照中 capability keys 的注释已有先例警示（自由文本、无注册表、"a model can name anything here"、永不做闸输入，`predispatch_gate.go:85-88`）。

## 5. 剧本承载策略（Playbook as Policy Carrier）

### 5.1 为什么挂剧本在结构上是对的

- 既有原则「收口（exit）从属剧本」——「走多深」只在剧本内有意义。**「打到哪一步需要人点头」与收口同类，是打法的一部分**。
- 剧本作者是人，最清楚这套流程哪一步动仓库、哪一步只读日志。**剧本声明的自治/风险姿态是人签字的声明式事实**，足以支撑 §4.5，无需再给技能市场贴平行标签。
- 模板 spec 已有 `risk_policy` 雏形（`software_delivery` 的 `release_requires_human: true`）。本方案是扶正，不是发明。
- 符合宪法「场景差异用模板、画像、标签、Policy 与服务端校验表达，不进核心流程代码」。

### 5.2 三层分工（每层只回答一个问题）

| 层 | 回答的问题 | 承载 |
|---|---|---|
| 剧本（租户级模板） | 这类仗怎么打、打到哪要人点头 | 骨架、角色、收口、**`autonomy_default` + `autonomy_ceiling`** |
| 项目 | 在什么场地、用什么资源打 | 信封（能力供给与 Chat 默认面）、编制、runtime、**可再收紧的策略上限** |
| 发起面 | 谁授权、何时授权 | 规则/集成在剧本上限内选档；交互发起可临场更严 |

**边界：剧本只声明「要求与上限」，不承载「供给」。** 剧本可以说「本打法涉及仓库写操作」（风险姿态），不可以说「本打法自带这五个技能」——技能/MCP 供给的事实源仍是项目绑定 + 员工常备，防止剧本变成 god object、与信封抢事实源。

### 5.3 合成规则：单向阀

> **有效档位 = min(剧本上限, 项目上限, 发起面所选档)。任何一层只能比别人更严，永远不能替别人放松。**

- 剧本声明 `autonomy_ceiling`（本打法最多允许多自动）+ `autonomy_default`（推荐档）。
- 项目可整体收紧（如「本项目一切需人批」压过任何剧本）。
- 规则/集成配置时，档位选项**只显示 ≤ min(剧本上限, 项目上限)**，保存时服务端校验。

### 5.4 单调性：运行期永不比配置期更松

- 剧本改版**收紧**上限 → 引用它的存量规则 fire 时降级为更严的档，park/拒 + 通知（与编制失效处置同构）。
- 剧本改版**放松**上限 → 存量规则**不**自动跟随；要用更宽的档必须有人回去重新保存规则（重新签字）。
- 推论：剧本编辑不构成静默放权后门；剧本策略字段变更进审计。

### 5.5 chat 不强制剧本（不变量保持）

Baseline 不变量 4「chat 不强制剧本、不产生 demand」不动。chat 自动化规则**可选**引用剧本取目标模板与策略档；交互 Chat 走信封 + 轻确认，不引入「先选剧本才能对话」。

### 5.6 留白：按 exit 档细分策略上限

Exit 本身分档且「走得越深副作用越大」，策略上限理论上可按 exit 档细分（浅档全自动、深档人批）。第一版**不做**（整剧本一档）；将来出现「同一剧本巡检全自动、修复要人批」的真实诉求时，答案是挂 exit 档，**不是**给规则开闸点矩阵，也**不是**给技能贴风险标签。

### 5.7 项目级策略上限落点（拍板：并入 `coordination_policy`）

**它解决什么问题：** 剧本说「这类仗可以全自动」，但某个具体项目（例如生产仓）可能要求「在本场地再严一档」。项目级 `autonomy_ceiling` 就是单向阀里的「项目上限」——只能收紧，不能替剧本放松。

**两个候选：**

| 落点 | 含义 | 利 | 弊 |
|---|---|---|---|
| A. 并入 `coordination_policy` | JSON 内新增 `autonomy_ceiling`，与既有 `require_human_review_for_new_demands` / `max_plan_iterations` 同袋 | 同属「本项目协调自治边界」；配置页已有「协调策略」tab 与修订流；不加新列，避免再造无消费者的顶层字段（`approval_policy` 教训） | 名字上「coordination」偏 plan/loop，Chat/API 读同一字段时需文档写清「项目自治上限，跨调用面」 |
| B. 独立列 / 独立 JSON | 例如 `projects.autonomy_policy` | 命名更直白 | 多一套读写/契约/配置面；易沦为第二份死策略；与 `require_human_review_for_new_demands` 语义重叠后难合成 |

**拍板：A。** 在 `coordination_policy` 增加 `autonomy_ceiling`（枚举与规则档位同族；缺省 = 不额外收紧，即仅受剧本上限约束）。既有 `require_human_review_for_new_demands` **保留**，语义收窄为「新 demand 的计划确认是否强制人批」的细闸；合成时两者同时生效（细闸不能被 ceiling 的宽松档绕过）。实施时在协调策略 UI 用中文说明「自治上限作用于本项目所有发起面（自动化 / API / 交互）」，避免用户以为只管 Temporal 协调。

## 6. 项目级剧本绑定退役（本次拍板 5）

### 6.1 语义依据

剧本是「这类仗怎么打」的**租户级模板**，与某个项目无固有绑定；发起一单需求时才知道这单是什么仗。项目创建时绑定默认剧本混淆了「模板库」与「使用现场」两个层次，且让「项目默认」成为一条静默的剧本命中路径——用户在发起时看不到自己「被选了」哪个剧本。

### 6.2 现状盘点（实施前须重新核对消费点）

| 对象 | 现状 | 处置 |
|---|---|---|
| `projects.scenario_template_key` | 建项目时可选绑定，可空（`058_scenario_templates.sql:42,56`） | **删列**（迁移） |
| 建项目向导「场景模板」选择器 | `create-project/project-basics-step.tsx` | **删除**该步骤字段 |

## 8. 外部 API 外放

定位：**带信封的预授权执行入口**，不是「远程任务中枢」也不是「远程收件箱」。

- 开通集成时（有人在场）拍板：绑哪个项目、哪个员工（或角色 → 编制解析）、信封（skill/MCP 集）、模式（chat 旁路 / plan|loop 进主轨）、剧本与策略档（受 §5.3 单向阀约束）、预算（频率/并发/写面）。
- 每次调用：鉴权 → 信封与策略 enforce → 静默执行或明确拒绝。**不产生**「待审批调用单」。
- 第一版只开放两个动词：**信封内 chat run** 与 **提交 plan/loop demand**。不开放「通用代理任意对话且边跑边审」。

### 8.1 P5 实施拍板（用户 2026-08-13 上午，逐条不得静默偏离）

| # | 问题 | 决议 |
|---|---|---|
| 1 | 集成绑定落点 | **新表**（`external_integrations`），不复用 Connector（Connector 是出站消息通道，入站 API 绑定是独立业务对象） |
| 2 | 服务鉴权形态 | **专用 integration token**（新表，与 `auth_service_tokens` 分家；明文只显示一次，可独立吊销/轮换） |
| 3 | 信封/剧本/自治档固化 | **活引用 + 单向阀**：绑定存开通时选的档位、可选剧本 key、信封 skill_ids；每次调用现算 `Effective(剧本上限, 项目上限, 绑定档)`，信封与项目 skill 绑定面现算交集。项目/剧本**收紧立即生效**；放松**不**自动升档（与 P2/P3 automation 语义一致，防静默放权） |
| 4 | 频率预算事实源 | 第一版**每集成简单计数硬闸**（每小时调用数上限，绑定行上固定窗口计数），超限 429 + 审计；并发/写面/成本预算后续完善 |

**P5 纠偏补充（2026-08-13 复审落地）**

- 空 `skill_ids` **不是**项目 Chat 默认面：`allow_chat_run` 开通时须显式非空信封；调用时 `binding ∩ project_bindings`，空交集拒。
- `ExecuteDemandSubmit`：Effective ≠ `full_auto` → **同步拒**（`ErrPolicyReject`），不建单、不进收件箱。
- 协调闸防御：外部 demand 若仍撞闸且 Effective ≠ `full_auto`（例如提交后 ceiling 收紧）→ policy **reject**，不 park（自动化 `pause_at_gate` 仍 park）。
- Chat 动词仍不因档位拒跑（无 human 闸碰撞）；仍现算 Effective 供活引用/审计。

## 10. 已否决方案（连同理由，防止重议）

| 方案 | 否决理由 |
|---|---|
| Chat 全面只读/沙箱降级（A 路线） | tri-mode §11 已否；Chat 是人直接下令，不应废成纯参谋；B 路线补能力面闸即可 |
| 收件箱审每条 Chat / 每次 API 调用 | 把旁路拖回审批轨，功能失去意义；治理前移到配置时刻 |
| 「无审批」= 跳过闸点 | 审计断链、状态机分叉、无法收紧；正确语义是 resolver=policy（§4.2） |
| 无判据的无条件自动验收 | 橡皮图章比没有闸更糟（§4.3） |
| 风险档采用模型自报输入 | `predispatch_gate.go:85-88` 先例：自由文本不做闸输入（§4.5） |
| skill/MCP/Capability 独立风险标签体系（第一版） | 与剧本自治姿态重复；配置面翻倍、双事实源；差异化由场景模板承担（拍板 4） |
| 项目级 `autonomy_policy` 独立列/袋 | 与 `coordination_policy` 重叠；易重演死策略字段；拍板并入 `coordination_policy.autonomy_ceiling`（§5.7） |
| 剧本承载能力供给 | 与项目信封抢事实源，剧本变 god object（§5.2） |
| 剧本放松即存量规则自动跟随 | 剧本编辑变成静默放权后门；单调性规则（§5.4） |
| 交互确认扩展到自动化/API | 无人在场无确认语义；撞 human 只能 park 或拒（§4.4） |
| 先造策略配置面再找消费者 | `approval_policy` 死因重演（§1.3） |
| API 同步调用撞 human 转异步等待 | 第一版复杂度失控；显式拒绝 + 独立立项异步语义 |

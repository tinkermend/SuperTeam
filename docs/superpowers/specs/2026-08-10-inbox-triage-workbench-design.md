## 1. 核心职能

收件箱是**人类在平台里的唯一待办入口**（`2026-07-24-human-task-unification.md` §6.1）。它承担的动作链是：

> 扫读「有什么 / 哪个最急」→ 判别「这条要我判什么」→ 就地决断 → **继续下一条**

下面五个缺陷分别打在这条链的各环上：D1/D2 打第一环（哪个最急），D3/D4 打第一二环（有什么 / 要我判什么），D5 打第四环（继续下一条）。

## 2. 现状诊断

### 2.1 D1 · 组内排序是「最近活动」，而代码注释声称是「风险」

[inbox-item-list.tsx:66-67](../../../apps/web/src/features/inbox/components/inbox-item-list.tsx#L66) 的注释写着：

> 组内保持上游顺序（**上游按风险/关注度排序**），不再二次排序。

**这个前提不成立。** 服务端唯一的排序是 [inbox.sql:196](../../../apps/control-plane/internal/storage/queries/inbox.sql#L196)：

```sql
ORDER BY last_activity_at DESC, created_at DESC, id DESC
```

`rg 'risk_level' apps/control-plane/internal/storage/queries/inbox.sql` 的全部命中都在**过滤条件与 upsert 列**里，`ORDER BY` 中从未出现 `risk_level`。上游从来没有按风险排过序。

后果：前端因为这句错误注释**主动放弃了二次排序**，组内顺序纯粹是时间序（见 2.3 的实测序列）。

### 2.2 D2 · 跨组顺序是固定领域序，与紧迫度无关

[INBOX_CATEGORY_ORDER](../../../apps/web/src/features/inbox/components/inbox-item-list.tsx#L68) 是硬编码固定序：计划确认 → 执行放行 → 下游放行 → 验收签署 → 结项确认 → 异常处理。

高风险事项按 `kind` 天然散落在各组，而「计划确认」恰是最常见、**结构性偏低风险**的一类（计划尚未执行）。于是最常见的低风险组永远占据首屏，把跨组的高风险项压到折叠线以下。

**这不是 §6.1 的要求。** 分组的授权出处 `2026-07-24-human-task-unification.md` §6.1 只写「按 layer 分组呈现」，**对组间与组内排序只字未提**。固定领域序是实施期的自由发挥，不是承重约定。

### 2.3 D1+D2 的线上实测（2026-08-09 23:35，16 条 open）

页面在**五处**承诺「按紧迫度分诊」：

| 承诺处 | 内容 | 代码 |
|---|---|---|
| 页面副标题 | 「高风险与阻断项**优先处理**」 | [inbox-shell.tsx:160](../../../apps/web/src/features/inbox/components/inbox-shell.tsx#L160) |
| KPI 卡 | 「高风险 5」「阻断 0」，>0 点亮语义色 | inbox-shell.tsx `InboxSummaryCards` |
| 列表头 | 「5 高风险」计数 pill | inbox-item-list.tsx `highRiskCount` |
| 行左侧 | danger / warn accent bar 按 `risk_level` 着色 | inbox-item-list.tsx `accentShadow` |
| 行内 CTA | **仅** blocked/high 渲染主按钮（`2026-08-07` spec §5.1） | inbox-item-list.tsx `primaryAction` |

**但整条管道无一处按风险排序。** 实测：KPI 显示高风险 5；首屏（列表滚动容器 `top=328/bottom=1067`，高 739px）完整可见 **4 行，其中高风险 1 行**；另 4 条位于 `top=1449/1632/1786/1969`，全在首屏之下。

```
计划确认   0:高  1:低  2:中  3:低  4:低  5:中  6:中     ← 组内明显不是风险序
执行放行   7:高
验收签署   8:高  9:高
结项确认  10:高
异常处理  11:低 12:低 13:中 14:中 15:低
```

唯一在首屏的那条高风险（index 0）是**按更新时间碰巧排最前**，不是任何规则的结果。

**与 §5.1 行内 CTA 相互抵消**：那批 CTA 被特意限定在 blocked/high 上以缩短决策路径，结果恰好全部落在首屏之下——**为缩短路径而加的控件本身需要先滚动才能看见**。

### 2.4 D3 · 信息层级倒置：标题位放的是常量，真身份被压成 11px 灰字

一条 `plan_review` 行渲染 9 个文本元素。在 7 条 `plan_review` 行（共 16 行）里：

| 元素 | 视觉权重 | 区分度 |
|---|---|---|
| 标题「确认项目计划版本」 | **最大最粗**（`text-sm font-bold text-ink`） | **7 行完全相同** |
| why「计划版本需要你确认后才能开始执行」 | 独立段落 `text-xs` | **7 行完全相同**（`humanTaskWhy` 静态 switch 返回值） |
| 进度条 +「计划确认 待你 → 执行 未开始 → 验收 未开始 → 结项 未开始」 | **占满整行宽** | **7 行完全相同** |
| 类型 pill「项目决策」 | pill | **16 行全部相同**（当前 open 全是 `project_decision`） |
| planner 摘要 | 2 行 clamp `text-ink-2` | 有区分度 |
| 需求名「F1判别验证-浅出口」 | **`text-[11px] text-ink-3`，meta 行内** | **这才是真正身份** |

**常量拿走标题、全宽进度条、一个 pill 和一整段说明；变量被压成灰色小字。** 扫读时看到 7 个一模一样的「确认项目计划版本」，必须逐行读小字才能分辨。

### 2.5 D3 的根因：`title` 字段有 6 种互不一致的写入约定

服务端写 `TitleSnapshot` 时每个 kind 各写各的：

| kind | 线上 `title` 实样 | 约定 |
|---|---|---|
| `plan_review` | 确认项目计划版本 | **kind 常量** |
| `dispatch_release` | 高风险动作需要确认 | **kind 常量** |
| `casting_expansion` | 扩编请求 | **kind 常量** |
| `acceptance_sign` | 需求验收：B3 H4 judge 10:18:33 | kind + 需求名 |
| `closure_confirm` | 结项确认 · 批三 H1H4 全链路 181601 | kind + 项目名 |
| `project_task_*` | 读取README并总结仓库用途 / 采集数据 | **纯任务名，无 kind** |
| 告警类 | 编制失效：批三 H1H4 全链路 181601 / 飞书通道失联 | 自带完整身份 |

前端把该字段当"标题"直接渲染，于是三分之一显示常量、三分之一显示"kind+身份"、三分之一显示裸身份。**没有任何一种是一致的。**

### 2.6 D4 · 行密度：常量吃掉大部分视觉预算

实测行高约 **148px**，16 条共 2368px，滚动容器高 **739px** —— 看完 16 条要滚 3.2 屏。其中 why、进度条、类型 pill 三项（约占行高一半）在同 kind 内零信息量。

### 2.7 D5 · 没有队列回路

| 能力 | 现状 | 代码 |
|---|---|---|
| 行间键盘导航 | **无**。仅 Enter/Space 选中当前焦点行 | [inbox-item-list.tsx:176-181](../../../apps/web/src/features/inbox/components/inbox-item-list.tsx#L176) |
| 焦点成本 | 每行含 CTA + 「查看上下文」两个 tab stop，16 行约 48 次 Tab | 同上 renderRow |
| 处理完自动前进 | **无**。成功后选中项消失，`useEffect` 清空 `selectedItemId`，回到"什么都没选" | [inbox-shell.tsx:150-154](../../../apps/web/src/features/inbox/components/inbox-shell.tsx#L150) |
| 批量处理 | **无** | `rg 'checkbox\|selectedIds\|bulk' features/inbox` 零命中 |

结果：连续处理 N 条＝N 次「定位 → 选中 → 决断 → 失去位置」。

### 2.8 与既有结论的关系

原始外部审查提出「收件箱＝裁决工作台，不是事项浏览器」，方向正确。`2026-08-07` spec 否决的是它给的**落法**（列表内一键提交，不安全，见该 spec §5.1），但当时**未质疑行形态本身**，把问题当作逐条局部缺陷修，属处理偏保守。本文补上这一层。

## 3. 设计张力（先承认，再选边）

分组与紧迫度排序服务两个**都真实**的目的：

| 轴 | 回答的问题 | 价值 |
|---|---|---|
| 按 kind 分组（现状） | 「系统在要我做哪一类决策」 | 同类可批量心智处理 |
| 按风险排序 | 「我下一个该处理哪个」 | 分诊；避免高风险沉底 |

一块屏幕上二者会冲突。**不能靠"都要"糊过去**——那正是现状：视觉上到处标风险，排序上完全不看风险。

**本文立场：收件箱首先是分诊面**（2.3 的五处设计都按这个立场），分组是次级组织手段。因此紧迫度应能**穿透**分组，但不应**取消**分组。

## 4. 方案（按实施阶段编号）

### 4.1 阶段 1 · 服务端风险优先排序（治 D1）

**改法**：[inbox.sql:196](../../../apps/control-plane/internal/storage/queries/inbox.sql#L196) 的 `ListInboxItems`：

```sql
ORDER BY
  CASE risk_level
    WHEN 'blocked' THEN 0
    WHEN 'high'    THEN 1
    WHEN 'medium'  THEN 2
    WHEN 'low'     THEN 3
    ELSE 4                      -- NULL / 未登记值排在最后，不得插队
  END,
  last_activity_at DESC, created_at DESC, id DESC
```

**为什么改服务端而非前端二次排序**：

- `LIMIT/OFFSET` 存在（默认 `limit=50`，[inbox-query.ts:6-10](../../../apps/web/src/features/inbox/inbox-query.ts#L6)）——前端只能重排**当前页**，翻页后高风险仍会被截断到下一页。分页边界上前端无解。
- 收件箱读路径不止 Console 一个消费方（飞书 connector 同源），排序语义应当只有一处。
- 顺带让 [inbox-item-list.tsx:66-67](../../../apps/web/src/features/inbox/components/inbox-item-list.tsx#L66) 那句注释**第一次变成真的**——实施时必须同步修订该注释，注明排序契约现由 `ListInboxItems` 承担。

**性能**：当前无 `(tenant_id, risk_level)` 索引，但按租户过滤后规模是百量级（线上 50 行），`CASE` 排序不构成问题。**不要顺手加索引**——无证据，属过早优化。

> **副作用：「等待最久」KPI 口径会静默改变。** 该指标是**前端基于当前页 `data.items` 算的**（[inbox-shell.tsx:140-148](../../../apps/web/src/features/inbox/components/inbox-shell.tsx#L140)；服务端 `summary` 只有 open/high_risk/blocked 三个计数，没有它），而 `limit=50`。今日按 `last_activity_at DESC` 取，这 50 条是「最近活动的 50 条」；改风险优先后变成「风险最高的 50 条」，该 KPI 遂从「所有待办里等最久的」变成「高风险里等最久的」，**数字变小且无人察觉**。当前 16 条未触上限故不显现，属潜伏漂移。处置见 U6。

**为什么放第一阶段**：改动极小、纯后端、零视觉变动、零截图重拍；且**它决定后续阶段的首屏判据基准**——先定排序，阶段 2 的首屏容量实测才是终态。

### 4.2 阶段 2 · 行身份重排 + 密度压缩（治 D3/D4）

#### 4.2.1 身份重排：`layer` 驱动的结构化组合

行标题不再取 `item.title`，改为按 `HumanTask.layer`（§4.1 既有模型，服务端已下发）组合：

| `layer` | 标题位取值 | 兜底 |
|---|---|---|
| `demand` | 需求名（`primaryDemandLabel`） | 缺失 → `missingObjectLabel("demand", id)` |
| `task` | 任务名（`source_task_name`） | 缺失 → `missingObjectLabel("task", id)` |
| `project` | 项目名（`source_project_name`） | 缺失 → `missingObjectLabel("project", id)` |
| 无 `layer`（告警类） | `item.title` | —— |

**线上覆盖率实测（16 条 open，零缺口）**：

```
layer=demand  (11) : plan_review 7 / casting_expansion 2 / acceptance_sign 2  → has_demand  11/11
layer=task    ( 4) : project_task_clarification/runtime_recovery/recovery 3
                     + dispatch_release 1                                      → has_task     4/4
layer=project ( 1) : closure_confirm 1                                         → has_project  1/1
无 layer           : automation_alert / channel_alert / casting_invalidated     → title 自带完整身份
```

**为什么按 `layer` 而非按 `kind` 列举**：`layer` 是 §4.1 已定义的模型字段（[humantask/kind.go:10](../../../apps/control-plane/internal/humantask/kind.go#L10) 的 `KindAndLayer`），新增 kind 自动归位；按 kind 硬列会在每次加 kind 时漏改。

**为什么在前端组合而非让服务端统一 `TitleSnapshot` 约定**：`TitleSnapshot` 是**已落库的历史快照**，改服务端约定不修历史卡；前端已持有全部结构化片段（`2026-08-07` spec §3.1 补名后 `demand_title` 齐备）；`title` 仍保留为兜底与告警类的唯一来源，不作废该字段。

**kind 降为行内 pill**：原标题里的 kind 语义改由 kind pill 承担（`humanTaskKindLabel`），与风险 pill 并列。

> **与 `2026-08-07` spec §3.3 的边界（实施时必须在代码注释写明）**：§3.3 让 meta 行不再回退 kind，理由是「与分组表头恒等重复」。本文把 kind 提升为**行内 pill**，位置与角色都变了——分组表头说的是"这一段属于哪类"，行内 pill 说的是"这一条属于哪类"，在阶段 4 的优先区（跨 kind）与时间档（不分组）里后者不可省。不写明，下一个人会当成 §3.3 回归删掉。

#### 4.2.2 密度压缩：148px → 约 68px

**行内保留**（两行结构）：

```
┌────────────────────────────────────────────────────────────┐
│ ▌ F1判别验证-浅出口            [计划确认] [低风险]  1 天前   │
│   仅需在 README 加简介并交付分支，无审查与发布                │
└────────────────────────────────────────────────────────────┘
  ↑accent  ↑身份(标题位)          ↑kind    ↑风险      ↑相对时间
```

- 第 1 行：风险 accent bar + **身份**（4.2.1）+ kind pill + 风险 pill + 相对时间 +（blocked/high 时）行内 CTA
- 第 2 行：`summary` **单行 clamp**（现为 2 行）

**移出行、迁入右侧详情栏**：

| 元素 | 去处 | 说明 |
|---|---|---|
| `why` | 详情栏「为什么需要你处理」区首行 | 同 kind 内是常量，行内零信息量；详情栏对单条仍有价值 |
| 进度条 + label | 详情栏（**新增**） | **注意是搬不是删**：`rg 'InboxProgressBar'` 证实它当前**只在列表命中、详情栏根本没有** |
| 类型 pill「项目决策」 | **删除** | 16/16 恒同；`item_type` 已由 kind pill 更精确表达 |
| 完整 `summary` | 详情栏（已有） | 行内只留单行 clamp |

「查看上下文」链接的去留见 U3。

**预期**：16 条 × 68px ≈ 1088px，1.5 屏（现 3.2 屏）。

### 4.3 阶段 3 · 队列回路（治 D5）

#### 4.3.1 键盘导航

- 列表实现 **roving tabindex**：只有当前行 `tabIndex=0`，其余 `-1`；`ArrowUp`/`ArrowDown`（及 `j`/`k`）在行间移动并同步选中，**跨分组连续移动**；`Home`/`End` 跳首尾。
- 行内 CTA 与链接从 Tab 序移除（`tabIndex=-1`），由行级快捷键触达（见 U4）；这把 16 行的 tab stop 从约 48 降到 1。
- `Enter` = 打开当前行主动作弹窗（等价于点行内 CTA）；`Esc` 在未开弹窗时清除选中。
- 与 `2026-08-07-task-hub-ux-remediation-design.md` §4.3 的 roving tabindex 同法，实施时对齐其实现。

#### 4.3.2 处理完自动前进

**现状**：成功 → 列表 refetch → 该项消失 → [inbox-shell.tsx:150-154](../../../apps/web/src/features/inbox/components/inbox-shell.tsx#L150) 的 effect 发现选中项不在列表里 → 清空选中。

**改法**：在**提交前**记下当前项在当前渲染序列中的位置，成功后把选中态移到**同位置的新占位项**（即原列表的下一条）；已是最后一条则选中新的最后一条；列表为空则清空。

> **必须保留原 effect 的兜底职责，两条语义不得互相污染**：选中项因**他人处理**（SSE 推送）而消失时仍应**清空**而非跳走——用户没做动作却被移动选中态是更糟的体验。因此新逻辑**只在本次提交成功的回调里**生效，不改 effect 语义。

### 4.4 阶段 4 · 优先区 + 排序切换（治 D2，含判断点）

> **本阶段起手先做一次实测，再决定 4.4.1 是否要做。** 阶段 1+2 完成后，行高降到约 68px、加 5 个分组表头约 140px，739px 容器可放约 8–9 行；当前 5 条高风险在 index 0/7/8/9/10，预计约 **3 条**落入首屏（现为 1 条）。**先量实际值**：若已达到可接受水平，4.4.1 可降级或不做；若仍有高风险在折叠线下，按下述实施。**不要不量就建。**

#### 4.4.1 置顶「优先处理」区

`groupInboxItems`（[inbox-item-list.tsx:88](../../../apps/web/src/features/inbox/components/inbox-item-list.tsx#L88)）在现有领域分组**之前**产出新分区：

- 分区键 `priority`，表头「优先处理」+ 计数；
- 纳入条件：`status === "open"` 且 `risk_level ∈ {blocked, high}`（口径见 U1）；
- 被纳入的事项**从其领域分组移除**，不重复渲染（同一事项出现两次会让计数与"处理完了吗"的判断失真）；
- 分区内顺序沿用上游（阶段 1 之后即风险优先 + 时间序）；
- 分区为空时整块不渲染。

**每行仍显示 kind pill**（4.2.1 已保证）：优先区打散领域上下文，无 kind 用户看不出这是「验收签署」还是「执行放行」。

**为什么不是「按组内最高风险动态排序分组」**：那样分组位置会随事项增删跳动（最后一条高风险被处理掉，整个组突然下沉），破坏肌肉记忆；固定领域序的唯一价值恰是位置稳定。抽出到独立分区既拿到分诊，又不动原分组相对位置。

#### 4.4.2 排序切换：默认风险优先，可切「等待最久」

**动机（一个实测到的死角）**：KPI 第四张卡叫「等待最久 101.6h」，但当前**没有任何方式定位到那一条**——这个指标现在是死胡同。加上该排序它才第一次可点。

1. **契约**：`GET /api/v1/inbox/items` 新增 `sort` 查询参数（现有参数只有 `view/status/item_type/risk_level/project_id/target_user_id`，无排序参数）：

   | 值 | 语义 | `ORDER BY` |
   |---|---|---|
   | `risk`（默认，缺省即此） | 分诊 | 阶段 1 的 `CASE risk_level` + `last_activity_at DESC, created_at DESC, id DESC` |
   | `oldest` | 积压：谁被晾最久 | `created_at ASC, id ASC` |
   | `recent` | 变更：我不在时什么动了（即今日行为） | `last_activity_at DESC, created_at DESC, id DESC` |

   `sort` 取非法值时**回落 `risk`**，不报错、不空列表。是否做 `recent` 见 U7。

2. **必须做在服务端**：与阶段 1 同理由（`limit/offset`）。

3. **时间档摊平列表**：选 `oldest`/`recent` 时**不渲染优先区、不按 kind 分组**，只出一条平列表；行内仍显示风险 pill 与 kind pill。
   - 理由：用户选时间档就是在说「我要积压/变更视角，不要分诊视角」。若仍保留优先区与固定领域序，时间顺序只在组内生效，等于没选。
   - 控件上必须写明（如选项副文案「按等待时长排列，不分组」），否则是惊吓。

4. **只进 URL query param，不进 localStorage**（建议值，见 U5）：收件箱的职责是把紧急项顶到眼前；若持久化，偶然切过一次的用户会**永久停在非分诊视图**，高风险散落其中而无优先区兜底。URL 参数可分享、刷新保持，新导航回落安全默认。

5. **KPI 联动（可选）**：「等待最久」卡可做成点击即切 `oldest` 的快捷入口。加分项，不做也不算缺陷。

#### 4.4.3 副标题与承诺对齐

阶段 1 + 4.4.1 落地后副标题「高风险与阻断项优先处理」**首次成立**，无需改动。

反之，**若 4.4.1 被判定不做**（接受高风险散落分组里），则必须改副标题删去「优先处理」表述——不能让页面继续做一个排序上不兑现的承诺。**二选一，不得两者都不做。**

## 5. 明确不做

| 不做项 | 原因 |
|---|---|
| **批量处理** | 见 §5.1，这是一条被主动收回的范围 |
| 逐条分诊流（一次只呈现一条） | 人类已选定"不重做形态"；且会丢失总览能力 |
| 改分组模型或 kind 词表 | §6.1 承重约定 |
| 改服务端 `TitleSnapshot` 写入约定 | 治不了历史卡；4.2.1 在读侧解决且保留该字段为兜底 |
| 加 `(tenant_id, risk_level)` 索引 | 无证据支持；线上 50 行 |
| 虚拟滚动 / 分页 UI | 阶段 2 后 16 条仅 1.5 屏；阶段 1 已解决分页边界截断高风险的隐患 |
| 让优先区事项同时保留在领域分组里 | 重复渲染会让计数与完成判断失真 |
| 给 `risk_level` 建枚举约束 | 独立数据建模议题；阶段 1 的 `ELSE 4` 已 fail-safe |

### 5.1 批量处理：本批不做（这是对人类初始范围的一处收回，附理由）

人类选定范围时的选项描述含「同类低风险批量」。经分析**建议本批不做**：

1. **需求本身可能是 D3 的假象。** 想批量的冲动来自"7 条 plan_review 看起来一模一样"，而它们看起来一样**正是 D3 造成的显示缺陷**——它们其实是 7 个不同需求的 7 份不同计划。阶段 2 落地后它们不再长得一样，批量需求应重新评估再决定。
2. **与 2026-08-09 刚拍板的决定直接冲突。** `1e0494b3`（BREAKING）刚把 plan 模式改成**无条件停下等人类确认**，理由是「风控判据全由 planner 自填＝AI 判自己要不要给人看」。而 `plan_review` 恰是数量最多、最想批量的那类；批量批准 7 份计划＝不读计划就放行，正是该决定要消除的路径。

**处置**：阶段 1–3 落地并真实使用一段时间后，若批量需求依然存在，另行立项并单独论证安全边界（届时至少应排除 `plan_review` 与一切 `requires_comment` 动作）。阶段 3 的导航与自动前进已拿走连续处理的大部分成本。

**若人类推翻本条**：请明确指定可批量的动作白名单，实施会话不得自行扩大。

## 8. 实施顺序与理由

```
阶段 1（后端排序）
   └→ 阶段 2（身份 + 密度）──┬→ 阶段 3（键盘 + 自动前进）
                             └→ 阶段 4 判断点：先量首屏高风险条数，再决定优先区
```

1. **阶段 1 先行**：改动极小、纯后端、零截图重拍；且**决定后续阶段的首屏判据基准**——先定排序，阶段 2 的首屏容量实测才是终态；反序则那批判据要重测。
2. **阶段 2 是主体**：对应人类提出的核心不满，收益最大。建议 4.2.1（身份）与 4.2.2（密度）**各自单独提交**，便于把"身份变了"和"密度变了"两类视觉 diff 分开审；截图基线集中在 4.2.2 重拍。
3. **阶段 3 紧随**：与阶段 2 共同构成队列回路，一起验 T8/T9 更有意义。
4. **阶段 4 最后且带判断点**：优先区是对**列表结构**的补丁，其必要性与形态取决于阶段 2 后的实际密度（T6 已要求记录首屏高风险条数）。**先量再定，不要不量就建。**

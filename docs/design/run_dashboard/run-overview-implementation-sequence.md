# 运行总览实现顺序说明

日期：2026-06-19（Asia/Shanghai）
状态：设计推进说明，不是功能规格、接口细则或代码实现方案

## 1. 目标

本文件用于约束“运行总览”从概念图走向真实功能时的实现顺序。

最终目标是做出一个地图式运行总览：用户可以在一张办公室式的等距视图中查看多个团队、数字员工运行状态、异常情况、当前任务，并能从员工任务卡进入具体任务或流程详情。

本文件只定义大模块顺序和说明，不定义具体数据库结构、接口字段、组件代码、样式细节或动画实现。

## 2. 已确认边界

- 页面名称为“运行总览”。
- 第一阶段只做地图视图，不做表格视图。
- 不引入部门概念。
- 团队仍然是业务与治理单位。
- 楼层只是运行总览中的展示分组，不是组织架构、权限、预算或项目归属模型。
- 一个楼层建议最多展示 6 个团队。
- 团队区域采用办公室布局，每个团队显示团队名称、人数、状态汇总和重点数字员工。
- 数字员工状态灯用于表达运行态，例如异常、工作中、待人工确认、排队、空闲。
- 团队人数较多时，不强行展示所有员工；优先展示异常、工作中和需要关注的员工，剩余员工做数量聚合。
- 点击数字员工打开右侧任务卡。
- 点击“打开该任务”进入具体任务或流程编排详情。

## 3. 总体优先级

### P0. 产品边界与验收口径

先明确这张页面解决什么问题，以及第一阶段不解决什么问题。

本阶段需要确认：

- 运行总览服务于“观察运行态、发现异常、进入任务处理”，不是团队管理页，也不是流程编排页。
- 楼层只是展示分页，不改变团队、项目、员工的业务归属。
- 第一阶段不做复杂团队详情展开、不做部门管理、不做 3D 场景、不做自由编辑办公室布局。

如果这一层不先定，后续容易把运行总览做成新的组织架构系统，或者把漂亮图误当成功能本身。

### P1. 状态与数据口径

这是所有展示的基础，优先级高于布局模板和视觉资产。

本阶段需要统一：

- 数字员工运行态的来源。
- 团队状态汇总口径。
- 异常、工作中、待人工确认、排队、空闲的优先级。
- 员工当前任务、最近日志、证据、消耗信息的取数范围。
- 团队容量、已使用容量、空闲数量的统计口径。

重要原则：员工运行态必须来自任务、运行记录、Runtime、Provider、审批等真实事实推导，不应由前端硬编码或从员工静态状态字段直接推断。

状态解析优先级应先沿用现有运行态口径，例如待人工确认、异常、工作中、排队、空闲。视觉上可以突出异常和工作中，但不能为了视觉排序改变底层状态语义。

### P2. 后端运行总览聚合能力

在前端做地图之前，需要先有面向运行总览的聚合能力。

本阶段要完成的是能力设计，不是具体接口实现细节：

- 提供一个运行总览聚合入口。
- 能按楼层返回团队列表和每个团队的汇总状态。
- 能返回每个团队应优先展示的数字员工。
- 能返回未展示员工的聚合数量。
- 能返回右侧任务卡需要的当前任务、日志、证据和跳转目标。

不建议第一版由前端分别请求团队、员工、任务、运行记录、审批记录后自行拼装。这样会造成口径分散、刷新不稳定、状态不一致。

### P3. 布局与显示模板契约

确认数据口径后，再定义布局模板。

这里的模板指“展示模板”，不是业务模板。

模板至少需要描述：

- 楼层最多展示多少团队。
- 每个团队区域的位置和尺寸。
- 团队名称与统计卡片的位置。
- 办公室桌椅布局类型。
- 数字员工头像槽位。
- 状态灯位置。
- 溢出员工聚合位置。
- 数据刷新时座位是否保持稳定。

第一阶段建议只定义少量模板，例如：

- 小团队模板：适合 1-8 人。
- 标准团队模板：适合 9-18 人。
- 大团队模板：适合 19-32 人。

不要把模板做成纯手工坐标堆叠。正确方向是“固定槽位 + 模板类型 + 数据填充”，这样才能支持团队人数变化和多楼层展示。

### P4. 视觉资产与图标体系

视觉资产应在模板契约之后再做。

本阶段需要明确：

- 办公桌、椅子、电脑、墙体、地面、植物等是否使用 CSS/SVG 绘制。
- 数字员工头像使用真实头像、系统头像，还是生成头像。
- 状态灯、异常标记、待人工确认标记、排队标记使用哪套图标。
- 是否需要生成一套统一的等距办公资产。

第一阶段不建议先大量生成图片资产。可以先用 CSS/SVG 和现有图标系统完成结构，等模板稳定后再补充更精细的视觉资产。

### P5. 前端地图渲染骨架

本阶段开始进入前端功能开发。

建议技术方向：

- React 负责页面和交互状态。
- Tailwind 或现有设计系统负责基础样式。
- SVG/CSS 负责等距地图、办公室区域、连线和地面元素。
- DOM overlay 负责头像、状态灯、团队卡片、任务卡和可点击区域。
- 如需要拖拽缩放，可引入 d3-zoom。

第一阶段不建议使用 Three.js，也不建议为了这张图引入大型图编辑框架。运行总览本质是可视化运营界面，不是三维建模器。

### P6. 团队办公室模板落地

在地图骨架可用后，再落地团队办公室模板。

本阶段关注：

- 多种团队模板在同一楼层中的布局稳定性。
- 头像与桌椅位置是否对齐。
- 团队名称和统计信息是否清晰。
- 大团队是否能正确折叠空闲员工。
- 状态变化时座位是否保持稳定。

重点不是一次性还原所有视觉细节，而是确保团队数量、员工数量和状态变化时布局不会崩。

### P7. 核心交互闭环

视觉结构稳定后，再补齐交互。

第一阶段必须支持：

- 楼层切换。
- 团队选中。
- 数字员工选中。
- 右侧任务卡展示。
- 打开具体任务。
- 查看团队。
- 异常员工定位。

这些交互比动效更优先。没有这些能力，运行总览只是展示墙，不是控制台入口。

### P8. 动效与实时刷新

动效最后做。

可以逐步增加：

- 状态灯呼吸效果。
- 任务流向线动画。
- 异常闪烁提醒。
- 数据刷新过渡。
- 员工任务切换动效。

动效必须服从可读性。不能让页面变成装饰性动画，尤其不能干扰异常定位和任务入口。

实时刷新也应保证座位稳定，不能每次刷新都重新排列员工。

### P9. 真实数据联调与验收

最后用真实链路验证，而不是只看 mock。

验收时至少需要确认：

- 团队数量、员工数量、状态汇总来自真实 Control Plane 数据。
- 员工当前任务能正确展示。
- 异常、工作中、待人工确认、排队、空闲口径一致。
- 点击员工能打开正确任务卡。
- 点击打开任务能进入真实任务或流程详情。
- 楼层切换不会丢失选中状态或造成错误统计。
- 页面刷新、接口失败、空数据、大团队、多团队场景都有可解释表现。

## 4. 推荐阶段顺序

建议按以下顺序推进：

1. 先确认本文件中的边界和优先级。
2. 写运行总览数据口径说明。
3. 写后端聚合能力说明。
4. 写布局与显示模板说明。
5. 做一版低保真前端地图骨架。
6. 接入真实运行总览聚合数据。
7. 落地团队办公室模板。
8. 补齐员工任务卡和任务跳转。
9. 增加视觉资产和统一图标。
10. 增加动效和实时刷新。
11. 做真实链路验收。

## 5. 当前不优先做的事情

- 不先做 3D 场景。
- 不先做完整图片资产库。
- 不先做部门管理。
- 不先做表格视图。
- 不先做自由拖拽编辑办公室。
- 不先做复杂大屏动画。
- 不让前端自行拼装所有运行数据。
- 不把楼层字段做成核心组织架构字段。

## 6. 待后续确认的问题

以下问题不阻塞当前短文档，但会影响后续详细设计：

- 楼层分组由系统自动分配，还是允许管理员手动调整团队所在楼层。
- 团队内员工座位是否需要长期记忆，还是只保证单次刷新稳定。
- “查看团队”进入现有团队详情页，还是新增运行视角的团队详情页。
- “打开该任务”进入项目任务详情，还是流程编排实例详情。
- 数字员工头像优先使用真实头像、生成头像，还是统一系统头像。
- 运行总览是否需要 WebSocket/SSE 实时更新，还是第一阶段用轮询。
